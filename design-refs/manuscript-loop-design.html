The manuscript loop

ScriptAlly currently models the outbound half of querying: materials are bundled into packages, packages ride queries, tracking reports what came back. The inbound half — an agent's feedback prompting a revision, and that revision going back out — has no object in the app, even though R&R is already a first-class status. Versions close the loop. One append-only list on the manuscript; everything else references it.

1 · The loop

One new entity, three references
Value: every arrow below is a fact the app can already record or derive — versions add the dotted sage return path, which today ends in a status change and nothing else.
Manuscript The work. One record.
Versions Named orderings & revisions. Append-only.
Samples Excerpts from a version. Letters & synopses unchanged.
Packages Combinations of materials. Inherit the version through the sample.
Queries The activity log records which version each full or partial send carried.
Tracking Requests by opening. Who holds what.
← feedback · R&R · revision — a new version, linked to the activity that prompted it
Packages never reference versions directly — one edge only, sample → version, so the two can never disagree. This is the point I'm holding even though "versions inside packages" was the original suggestion.

"Latest" is a date fact, not a verdict. "From R&R" links to the activity that prompted it — the loop's return path made concrete. A manuscript with no versions shows none of this; the panel appears when the second version is created, because one version is just the book. Versions never count against the free tier's one-manuscript limit — orderings of one book are not multiple books.

6 · On the query

Activity log · one field
Value: consistency at the moment it matters. The agent read an opening; the app knows which; recording the send takes one pre-filled selection.
18 AUG← Full manuscript requested by R. Osei §Read: Prologue-first
19 AUG→ Full manuscript sent to R. Osei §Sent: Prologue-first ✓ matches what they read
"Read" is derived from the package that went out with the query. "Sent" is the one thing the writer selects, defaulting to what was read. A difference is stated — △ DIFFERS FROM WHAT THEY READ — and left alone, because sending a revision can be deliberate. `recomputeQuery` is untouched: the version is payload on the activity, never status.

7 · Deliberately not built

The fence
No file storage yet. Versions are records, not documents. When Storage lands, a version gains an optional file attachment — the design doesn't change, it gets a pocket.
No content verification, ever. The app cannot check that a sample's text matches its version. It records the writer's claim and says so.
No version editing beyond rename and note. A revision of the book is a new version, not an edit — append-only, like the activity log and querying goals. Archive hides; nothing is deleted while referenced.
No verdicts. "Latest" is a date. "Earlier version" is a count. No "outdated!", no prompts to chase agents, no recommended opening.
Queries never fragment. An R&R producing a new version continues the same query and the same log. Versions annotate the story; they never restart it.
Packages stay version-blind. They combine materials; the version rides in through the sample. One edge, no disagreement possible.
