What trying to break it turned up, in order of how much it matters.

1 · Date edits are the sharpest edge, not deletions. A deletion's consequences are obvious; a date edit that quietly reorders the log can flip status, move a chapter boundary, and re-anchor the window — all from a one-character change. The rule: any edit whose derived diff is non-empty gets the consequence sheet; an edit whose diff is empty skips it (card 6). Same engine decides both, so there is no second judgement to maintain. Card 2's middle option matters: half the time a crossing date means both dates are wrong.
2 · The root event is load-bearing. Editable, never removable — removing the send means removing the query, and that flow already exists (card 3).
3 · "Wrong query" is a move, not an edit — your own first example, and it needs its own verb: remove here, append there, two recomputes, one atomic undo restoring both (card 4). ⚠️ Root events cannot move; the target picker should surface each candidate's current status so a nonsensical landing (a Partial sent onto a query with no request) shows its consequence on the target side before commit.
4 · No future dates. The timeline records what happened; plans are reminders (card 5).
5 · Same-day ordering needs a stated tiebreak. Two events on 1 May already exist in the fixture — the derivation must order same-day events by a stable secondary key, and a date edit landing on an occupied day keeps insertion order rather than shuffling. ⚠️ CC must report what that tiebreak currently is; if the answer is "none", that is a pre-existing fault this work would expose.
6 · Undo must be atomic for cascades. "Remove both" and "Move it" are one undo each, restoring everything in one batch — never a toast per fragment.
7 · One free coherence, worth claiming: if Mark closed writes a closure event, then deleting that event is Reopen — the parked reopen CTA falls out of this work for nothing. CC should confirm closure is an event and not a stored flag before we bank it.
