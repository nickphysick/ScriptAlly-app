The fork is the design. Your two reasons are two different operations, and the menu says so in plain words before any form appears:
"I did it wrong""The agent changed their mind"
What it isThe record is falseThe record is true; the world moved
What happensEdit or delete the eventAppend a new event on top
HistoryChanges — it never happened that wayStands — superseded, not erased
Where it goesThe new edit surfaceRecord response / holding reply — flows that already exist
The second branch costs almost nothing: an agent reversing a decision is just the next response, and the machinery for that shipped weeks ago. The build is branch one.

How everything across the app reacts: it already does. Status, counts, chapters, windows, nudge availability, the waiting state's anchor — all derive from the activity log through recomputeQuery. Edit the log, recompute, and every surface follows by construction. That is the payoff of every derived-over-stored decision this app has made. The work is not propagation — it is three guards around the write:

1 · Consequences are shown before commit, not discovered after. Run the derived engine against the proposed log and diff the result — card 4 is that diff. The engine is pure, so running it ahead of the write is free, and the preview can never disagree with what actually happens because it is the same code.
2 · Dependency guards. Deleting a request that a send answers strands the send. The preview names the dependant and offers the three honest resolutions — never a silent cascade, never a refusal without a path.
3 · Undo, always. Every correction commits through the existing undo toast. A mis-correction of a mis-entry is the most human sequence imaginable, and it must cost one click.

⚠️ One decision for you: does a correction leave a trace? Derived-over-stored says the log is the truth and an edit simply changes it — no audit trail, which is right for a single-writer personal record. The alternative (a "corrected on" line on the event) adds honesty the writer may not want to see forever. My recommendation is no trace — this is the writer's own record of their own querying, not a ledger — but it is a product stance, so it is yours.
