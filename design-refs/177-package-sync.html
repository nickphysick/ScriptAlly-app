The sync runs one way, and that is the whole design. A package is a template; a send is a fact. Attaching copies the template's contents into the send and the copy never updates — so the Query Centre always shows what actually went, whatever happened to the package afterwards. Nothing flows back from the send to the package.

What the send stores is the snapshot plus a name and an id. The items are ordinary materials, exactly as if attached by hand; the package group around them is presentation, driven by that stored origin. That is why the pills stay individually editable and removable — ⚠️ and editing one out of the group does not "break" anything, it just means the send no longer matches the package, which is state 1.

The other direction is derived, not stored. The packages page's 4 queries sent with this package is a count over the queries whose sends carry that package id — never a list maintained on the package. ⚠️ Nothing writes to the package when a query is logged, so the two pages cannot disagree, and a deleted query simply stops being counted.

The three states exist so the writer is never quietly misled. State 1 appears only when the snapshot and the package actually differ — compare on render, show nothing when they match. State 2 keeps the name after deletion because the name is part of what happened; only the link goes. State 3 is the line the packages page already shows, now derived rather than assumed.

⚠️ One thing to decide: the illustration in the group header is a small ArtSlot — one image for all packages, or per-package? Per-package means a picker, a stored choice and an empty default; one shared mark costs nothing and reads as "this is a package". My recommendation is one shared mark now, per-package only if packages ever become numerous enough to need telling apart at a glance.
