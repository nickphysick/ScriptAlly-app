Query Centre — what versions actually touch

Four surfaces change, and one of them is a collision that decides build order. Nothing changes about status, and recomputeQuery is not touched — a version is payload on an activity, never a determinant of state. Everything marked is new.

Two additions
Scale: one derived line in the detail block, one chip on send rows in the timeline. No new components — the chip is the one already used on Submission packages.

2 · Logging a send

One pre-filled field
Scale: one select added to the existing record-response flow, on two activity types only — full sent, partial sent. Every other activity type is untouched.

Which version you actually sent. Change it if you sent something else — that's a fact worth recording, not a mistake.
Zero extra effort in the common caseThe right answer is already selected; the writer clicks Record. The field costs something only when the truth is unusual — exactly when recording it is worth anything.
Two activity types onlyFull sent and partial sent. Queries, replies, requests, rejections, R&Rs and resubmissions gain nothing and change not at all.
Free-tier writers see this tooVersions aren't a Pro feature — they're how the log stays truthful. A writer with one version never sees the field, because there's nothing to choose between.

4 · The collision

Correction UI · same territory
This is the finding. Both features work the same timeline rows in the same pane. Correction UI adds "Edit last entry" and the change-vs-mistake fork; versions add a field inside the thing being edited. Built in the wrong order, the second reopens the first.
The overlapCorrection UI's edit flow must handle every field on an activity. If versions land after it, the edit form gains a field the fork logic never accounted for — and "did the version change, or did I mis-record it?" is precisely the question that fork exists to ask.
Two sessions, one paneBoth touch timeline rendering and the activity write path. Concurrent sessions here would collide the way the header session collided with the broadsheet hero — but in the app's most load-bearing surface.
In order, they composeCorrection UI establishes the affordance and the fork. Versions then add one field that inherits both — the fork already knows how to ask its question about any field on an activity.
1
Correction UI
The oldest unbuilt item. editActivity/deleteActivity have been live in prod for weeks with no UI on them. Establishes the edit affordance and the change-vs-mistake fork.
2
Versions on the manuscript
The append-only list, the sample dropdown, the tracking panels. Touches Manuscripts and Submission packages — not the Centre at all, so it can run alongside or after.
3
Versions in the Centre
One pre-filled field on two activity types, one derived line, one conditional column. Inherits Correction UI's fork rather than reinventing it.

5 · What does not change

The fence
recomputeQueryUntouched. A version is payload on an activity and never participates in deriving status, response counts, revision rounds or pipeline dates. The single-writer rule holds.
Status and StatusDotNo new statuses, no new marks, no new colours. A version says what was sent, not where the query stands.
One query per relationshipAn R&R producing a new version continues the same query and the same log. Versions annotate; they never fragment.
The log's shapeOne optional field on two types. Append-only discipline unchanged; corrections go through Correction UI like any other field.
Writers with one versionSee none of it — no field, no column, no filter, no chips. The concept appears when a second version exists.
Free vs ProVersions sit on the free tier. They're truthfulness in the log, not a premium analytic — Requests-by-opening is where the Pro value lives.
