### From “Conventions & invariants” (CLAUDE.md lines 636–646)

- **⚠️ PLACE ART FROM ITS VISIBLE EDGE, NOT THE IMAGE BOX.** *(Contact list v11, 25 Sep — the Archivist; the capsule bar's 68.4%-ink wordmark is the same law's first sighting.)* A PNG's box routinely carries dead margin, so aligning the BOX to a column edge aligns nothing anyone can see: the v11 hero art was 810 wide with ink to 752, and "the art ends on the column's right" was `left + 752 × scale = column right` — a fact about the INK, held as named constants beside the file and solved by the layout chain, never re-measured by eye per breakpoint. When an asset is redrawn, the constants change WITH it or every placement silently means something else. *(The worked example is HISTORY since page header v2 deleted that hero, 27 Sep — recoverable at `d8eed30d` — and the law's live sightings are the wordmark and the hawk CROP, `scripts/crop-contact-hawk.mjs`, which erased the drawn card along a fitted ink line rather than a box edge.)*
- **⚠️ THE OUTER GAP LOOKS WRONG ON ONE SIDE — and the geometry is fine.** *(Symptom first, because the symptom points away from the cause.)*
  - **Symptom:** the right-hand margin looks smaller than the left.
  - **Cause:** it is not. Both are `--shell-cap-gap`. The left band is *padding + rail + gap*, so it is physically wider; and the pale rail reads as margin against the pale ground, which widens it again to the eye. **Re-measure with `getBoundingClientRect` before treating it as a bug** — measured 30 Jul, both gutters 14px.
  - **Fix:** none needed. **NEVER add right-side padding to compensate.**
  - **The one real way it can break:** a `position: fixed` floater measures from the BROWSER edge rather than the content capsule (the timeline pull tab sat at `right: 0`; the help FAB carried an inline `right`). That is a genuine bug with a genuine fix — give the escapee `var(--shell-cap-gap)` — but it is a *different* fault from the perceived asymmetry above, and it is not fixed by padding either.
  - The token is one value for every edge **and** the inter-capsule gaps: **`--shell-cap-gap: 14px`** (it spent a spell at 10px and was returned). *(The packs call it `--shell-gap`; the token in this repo has always been `--shell-cap-gap` — same thing, one owner: `.sv2-app { padding: var(--shell-cap-gap); gap: var(--shell-cap-gap) }`.)*

- **⚠️ A FORMAT THAT INHERITS ITS TYPOGRAPHY IS NOT A FORMAT — CLOSE IT, EVEN WHERE NOTHING RENDERS AT THE INHERITED SIZE.** *(30 Aug, the page masthead.)* `.wsh` set no `font-size` or `line-height`, and nothing inside it needed one: the kicker states 10px, the title 44, the description 16. What the inherited value governs is the **STRUT of the block's line boxes** — and the kicker is `display: inline-block`, so the line it sits on is `max(strut, the pill)`. The masthead's height was therefore a function of the page's own typography.
  - **MEASURED: 2.5px, on one page out of ten.** Query Centre renders under `.t-f12`, which inherits 13px/18.85 where the other nine inherit 16px/24. On the one element in the app whose entire claim is that it is identical everywhere.
  - **THE TELL IS AN INLINE-BLOCK, AN INLINE, OR ANY `em`/unitless-`lh` value inside a component that pages mount.** If a component's box depends on a value it does not state, it depends on every ancestor any page might give it.

### From “Conventions & invariants” (CLAUDE.md lines 664–690)

- **⚠️ A CONTROL WHOSE MEANING IS ITS GLYPH IS DRAWN, NEVER TYPED.** *(24 Sep, the rail's expand button.)* It rendered the character `⤢` (U+2922), which neither Special Elite nor this app's mono face carries, so the browser fell back and drew a dot: a control whose whole meaning is its arrow, showing none. **A character is a request to a font; a path is a picture.** The rule is not "avoid Unicode" — `✉`, `↺` and `✕` are all in use and all fine — it is that a glyph outside the Latin-1 and common-symbol range is checked in the app's OWN faces before it ships, and where the mark IS the control, drawn is the safe answer.
- **⚠️ THE APP HAS ONE NEAR-BLACK BUTTON FILL — `--btn-ink` (#1c130f) — AND ITS TWO CONSUMERS DELIBERATELY DISAGREE ABOUT THEIR TEXT.** *(30 Aug. ⚠️ HALF HISTORY SINCE 19 SEP: `+ New` was deleted with Query Centre v11, so the token has one consumer, `.wsh-cta`. The lesson — two literals one unit apart — stands.)* The top bar's `+ New` (`.ws-nbtn`) and the page masthead's primary (`.wsh-cta`) are the same object by design; before the token they were **two literals one unit apart** — `#1c130e` and `#1c130f` — invisible, unfindable, and on the two buttons whose entire justification is that they match. Both now read `--btn-ink`.
  - **THE FOREGROUNDS ARE STILL DIFFERENT AND THAT IS A DECISION, NOT AN OVERSIGHT.** `+ New` keeps `#ffffff`; the masthead reads `--btn-ink-on` (#fdfaf5). Nick's call: not worth a visible edit to the shell for a difference nobody can see. **Do not "fix" one of them** — unifying them by editing whichever file you happen to be in is how a THIRD value gets born, which is the exact fault the token was created to end.
  - **THE LOCK ASSERTS THE TOKEN FROM THE TOP BAR'S SIDE TOO** (`workspaceShell.test.tsx`, `mastheadFormat.test.tsx`). A token with one consumer would have left `+ New` on its own literal — i.e. the state it replaced, wearing a token's clothes.
- **⚠️ THE STATED FONT STACK AND THE RENDERED ONE DISAGREE, AND MOST OF THE APP IS ON SOURCE SANS PRO.** *(30 Aug, surfaced while retoning the masthead CTA.)* The stack is meant to be **Playfair · Inter · JetBrains Mono · Caveat**, and all four are loaded (`index.css:1`, `index.html`). But **`--font-sans` is `"Source Sans Pro"`** and Inter is named by exactly one selector — `--f12-body` on `.t-f12`, which is Query Centre. So every button, label and blurb that inherits is Source Sans Pro, and has been for some time.
  - **IT MATTERS THE MOMENT A REF SPECIFIES INTER.** The masthead CTA's brief did, with the rationale *"this matches `+ New` and the agent cards' `Log query`"* — and both of those declare `font-family: inherit`, so Inter would have made the masthead the ONLY Inter button in the family it was joining. The reason and the literal pointed opposite ways; the reason won.
  - **THIS IS EITHER A DRIFT TO CORRECT OR A STATED STACK TO UPDATE — Nick's call, not a code change to make in passing.** What must not happen is the two continuing to disagree while refs keep being written against the stack on paper.

- **⚠️ A `var()` ON A TOKEN NOBODY DEFINES IS A RULE THAT LOOKS PARAMETERISED AND IS NOT — AND IT SURVIVES EVERY SWEEP FOR THE TOKEN.** *(20 Aug, retiring the masthead's `--wsh-ctl-*` / `--wsh-pill-*` ladders.)* The tokens were deleted, and two page sheets were still READING them — `font-size: var(--wsh-pill-fs, 8.5px)`, `height: var(--wsh-ctl-h, 38px)`. Nothing broke, because a `var()` whose custom property has no definition falls back to its second argument. **That is exactly what makes it insidious: the page renders correctly, so no measurement catches it, and a grep for the token's DEFINITION finds nothing — which reads as 'already cleaned' rather than as 'still read'.** Meanwhile the next person to open that sheet sees a knob and goes looking for it.
  - **⚠️ THE SWEEP MUST BE FOR READS, NOT DEFINITIONS.** `grep -rn -- "var(--the-token" src` is the one that answers the question; `grep -- "--the-token:"` answers a different one and looks like the same answer. `shellV2Tokens.test.ts` already asserts the inverse for shell sheets — every `var(--x)` a stylesheet READS must resolve — and that lock is the reason this class is catchable at all.
  - **A FALLBACK IS FOR A TOKEN THAT MIGHT LEGITIMATELY BE ABSENT** (a page opting into a component's default). Once the token is retired, the fallback IS the value: state it, and delete the indirection.
  - **⚠️ AND THE OPPOSITE MISTAKE IS THE SAME SIZE: "THE TOKEN EXISTS" DOES NOT MEAN "THE TOKEN RESOLVES HERE".** *(25 Aug, sweeping this pack's fallbacks — the correction to the rule above, found by trying to apply it mechanically.)* A defined token still yields its fallback anywhere its **defining scope** is not an ancestor, so the identical construct can be dead weight in one file and the painted value in another. **Worked example, one token, two dispositions:** `--f12-serif` is defined once, on **`.t-f12`** — a theme class `Queries.tsx` applies and the packages page does not sit under. In `packageGroup.css` the token resolves and `var(--f12-serif, 'Playfair Display', serif)` is genuinely dead weight; in `packageTracking.css` it never resolves, so `Georgia, serif` is **what renders**, and deleting it as dead weight would silently have changed the font on a live surface.
    - **THE TEST IS THE SAME ONE THIS FILE ALREADY STATES FOR `--content-top-gap`: not "is it a token" but WHERE IS IT EVALUATED.** Before dropping a fallback, find the token's defining selector and confirm it is an ancestor of the rule's subject. `:root` always is; a theme class (`.t-f12`, `.t-capp`, …) is only sometimes.
    - **⚠️ A SOURCE LOCK CAN BE ASSERTING THE FALLBACK RATHER THAN THE VALUE.** `sentStrip.test.ts` read `toContain("Playfair Display")` and passed on the fallback string; the moment the fallback went, a lock about a family name failed over a font that had not moved. Assert the token where the value comes from a token.
    - **AND WHERE THE SCOPE ARGUMENT HOLDS, IT BEATS A SCREENSHOT.** A fallback applies only when the token is unset, so "the defining scope is an ancestor" proves the painted value cannot move — at every viewport and every theme, which one measured render does not.
    - **⚠️ AND A PORTAL IS THE CASE WHERE THE DEFINING SCOPE IS AN ANCESTOR OF NOTHING.** *(24 Sep, the Query Centre's expanded card — the same law arriving a third time, and the most expensive of the three because it was silent for two whole phases.)* `--qcv-*` was declared on `.qcv-page`; `QcExpanded` renders into `document.body`. **Every one of the 86 `var(--qcv-…)` reads in that card's two sheets resolved to NOTHING** — every ink, every parchment and all three faces — through two rounds of green measurement, because those measured geometry and literals. Measured: `background: var(--qcv-ink)` computed `rgba(0, 0, 0, 0)`.
      - **THE LAW WAS ALREADY LOCKED, FOR THE WRONG SUBJECT.** A lock said *"the MENU is portalled outside `.qcv-page`, so it reads NO page token"* — true, and a rule about one component, which had nothing to say when a second component portalled two phases later. **A law written about the component that happened to hit it cannot catch the next one; a law about the TOKEN can.** The sweep now requires any `--qcv-*` read across sheet boundaries to be declared at `:root`.
      - **⚠️ AND THE FIX IS `:root`, NOT A SECOND PALETTE.** `qcFan.css` and `taskModal.css` both portal and both declare their OWN prefix with stated values — right when the portal's palette is its own, wrong when the portal must be the page's colours, where it is two copies of one palette free to drift.
      - **⚠️ AND TAILWIND v4's `@theme { }` IS A `:root` BLOCK.** A sweep reading only a literal `:root {` reports `--font-sans`, `--font-serif` and `--font-mono` as defined nowhere. Verified in the BUILT sheet rather than assumed: `dist/assets/index-*.css` emits `@layer theme { :root, :host { --font-serif: … } }`. Reading the authoring syntax instead of the cascade is the same class as reading a source lock for a layout claim.
- **⚠️ NEVER SIZE TO THE VIEWPORT WITH A CONSTANT OFFSET. DERIVE THE HEIGHT FROM THE ELEMENT'S OWN MEASURED TOP.** *(Nick's rule, 21 Sep, replacing three separate anecdotes with one law — they were the same fault in three costumes and each was being rediscovered as though it were new.)* `100vh` is the VIEWPORT's height, never "the height remaining from here down", and `calc(100vh - <a number>)` is a guess at everything above the element — a guess that is wrong the moment a dismissible banner, a taller bar, a wrapped line or one extra card moves it. **The honest form is to measure the element's own `top` and publish it**, so the number is a fact about this render rather than a constant about one mockup.
  - **THE THREE IT REPLACES, kept for their evidence rather than their reasoning.** (1) **The Tasks chassis's unreachable 21px**: `.ws-main` sat below the beta strip at `y: 41.75` and still asked for a full `100vh`, so its bottom landed at 941.75 in a 900px viewport and the last 21px of every Tasks page was below the fold **with the document not scrolling** — it cost the Calendar the "Open the list" control pinned to the day panel's foot. (2) **The packages builder's sticky panel**: a sticky child caps itself to the SCROLLPORT, and `calc(100vh - …)` over-claimed by the shell's chrome — the honest cap was 664.4 where `100vh` gave 812.4. (3) **The Query Centre Overview's portal tiles** (21 Sep): the brief's own `calc(100vh - 430px)` was measured on a mockup whose page starts at the top of the window; here the strip, the bar and the head put the portal ~150px down, so the tiles ran 19px past the fold — with `scrollHeight === clientHeight`, so nothing scrolled and those 19px were simply unreachable.
  - **THE PUBLISHED MEASUREMENTS ALREADY EXIST — READ ONE RATHER THAN INVENTING A NUMBER.** `WorkspacePageGrid` publishes **`--wpg-port-h`** (its scroller's `clientHeight`) and **`--wpg-stuck-h`** (the pinned chrome's **settled** height — not the live one, or a sticky `top` bound to a value moving 62px mid-scroll takes the panel with it); the dashboard publishes `--os-port-h` and `--os-row2-top`; the Overview's portal publishes `--qco-avail`. **A lock asserting the scrollport and the viewport DIFFER** is what stops a run where they happen to agree passing by coincidence.
  - **⚠️ THE SAME DECLARATION IS CORRECT ONE ELEMENT UP AND WRONG ONE ELEMENT DOWN.** `.sa-shellframe` carries `height: 100vh` and is right, because it sits at `y: 0`. **Nothing in the declaration distinguishes them**, which is how this survives review every time. Before writing `100vh`, ask what is above the element — and whether anything ever could be.
  - **⚠️ A CONSTANT OFFSET ACROSS VIEWPORT HEIGHTS POINTS AT A FIXED-HEIGHT ANCESTOR, NOT AT PADDING.** The same 21px at 800, 900 and 1000, on three pages, cannot be proportional or content-driven — it is a fixed contribution counted once too many. Walk the ancestry for the first box whose bottom exceeds the viewport rather than hunting a stray `padding`.
  - **AND THE FIX IS OFTEN A DELETION.** `.ws-app` is a flex row and `.ws-main` is `flex: 1` inside it, so `align-items: stretch` already sized it correctly and the `100vh` overrode a right answer. **Never compensate with a matching offset** — that is the "add padding to fix a gutter" mistake this file already records.
  - **⚠️ AND REMOVING AN OVER-CLAIM LOOKS LIKE A REGRESSION DOWNSTREAM.** The Calendar had been drawing into 42px that did not exist; with the claim gone its rows are honestly 7px shorter and its cells began to overflow. **The overflow was always there — it was being drawn off-screen.** Budget for that rather than reverting.
  - **⚠️ AND A MEASURED TOP NEEDS A SENTINEL FOR "NOT LAID OUT YET".** A zero or negative rect is the page before layout, or a container the loading cover has `display: none`d — writing it publishes a wrong floor. The dashboard's row-2 clamp took its CEILING from a `top − portTop` of **−115** and rendered 560 against a loaded 383. Refuse the reading rather than storing it.

### From “Conventions & invariants” (CLAUDE.md lines 697–704)

- **⚠️ A PAGE'S CLASS AND A COMPONENT'S CLASS ON THE *SAME ELEMENT* ARE DECIDED BY SOURCE ORDER — SO A COMPONENT DEFAULT SILENTLY BEATS EVERY PAGE OVERRIDE.** *(21 Aug, the masthead's gutter.)* A page names itself with a className passed straight to the component (`<WorkspacePageGrid className="qc-wpg">`), so `.wpg` and `.qc-wpg` both land on ONE element at 0-1-0 and the later stylesheet wins. `--wpg-gutter: var(--content-gutter)` on `.wpg` therefore overrode `.qc-wpg`'s tight value on every page — **measured: Query Centre's content sat at 342 with the wide gutter while To-do's sat at 297 with the tight one, from declarations that read correctly in both files.** The old override worked only because it was `.qc-wpg .wpg-scroll` — a *descendant* selector at 0-2-0 — and flattening it to the token lost the specificity nobody knew was load-bearing.
  - **THE FIX IS A USE-SITE FALLBACK, NOT MORE SPECIFICITY.** `var(--wpg-gutter, var(--content-gutter))` at the point of use has no contest at all: the fallback applies only when nothing declared the token anywhere, which is exactly what "the page did not ask for a gutter" means. Raising specificity instead wins today and loses the day someone adds a third class.
  - **THE TELL** is a token declared on a component root that any page is also expected to set. **Ask where the page's class actually lands** — on the component's own element, or on an ancestor. Those two have opposite outcomes, and the second (inheritance from a nearer ancestor) cannot be fixed by specificity at all.
- **⚠️ NO ELEMENT'S POSITION OR SIZE MAY BE EXPRESSED AS A LITERAL THAT ANOTHER ELEMENT OWNS.** Either it is a shared token, or it is derived with `calc()` from one — and where an element's own size is involved, use `translate(-50%)` / `translateY(-50%)` so nothing has to know its own dimensions. *(26 Aug. Stated as one rule because four faults in a row turned out to be one fault, each found by measurement and each looking like a different bug.)*
  - **THE FOUR, because the shape is only recognisable from the set.** (1) **`--tl-head-h` DESCRIBING the header rather than setting it** — `min-height: 36px` against a header whose content rendered at 46, so the pinned row stuck ten pixels high and slid under the day names: the exact fault a token exists to prevent, committed by the token itself. (2) **A bar offset for a row height it did not own** — `LANE_STEP = 52` and `laneTop(lane) = lane * 52`, where the row's height was one expression and the bar's offset was another, both reading 52 and neither being the other's; measured, the bar sat at the TOP of its row with 96px of empty ground beneath it. (3) **A row not reserving space for its captions** — `--lane-h: 70px` beside a `34px` bar, where the 36px of slack was the caption strip: a number one element owned describing room a DIFFERENT element needed. (4) **A caption offset counted from the marker's BOX rather than its centre line**, so it moved whenever the marker's size did.
  - **THE TELL IS A NUMBER THAT APPEARS TWICE**, in two rules, for two elements, where changing one requires remembering the other. If you find yourself writing `calc(var(--x) - 8px)` for a second element's size, that second element wants its own token — the direction dot's `--ddot` was exactly that, written at three sites as an adjustment to the disc, and the density tiers move the two independently.
  - **AND A TOKEN BELONGS TO THE ELEMENT THAT OWNS THE FACT, NOT THE ONE THAT READS IT.** `--tl-head-w` was declared on `.tl-grid` — every row — which is where it is read; the today spine is a SIBLING of the rows, so it could not inherit it and would have needed a constant of its own. Moved to the board, one owner, and the rows and the spine are both readers.
- **⚠️ TWO WAYS TO EXPRESS ONE INSET — `padding` AND A `max-width` REDUCTION — AGREE UNTIL A CAP BINDS, THEN DIVERGE BY THE WHOLE INSET.** *(21 Aug, the same pack.)* The masthead was padded and the content was reduced (`min(cap, 100% - 2 × gutter)`), which is the same left edge while the cap is slack. The moment the cap binds, the reduction is **absorbed** — `min()` takes the cap and the gutter simply stops applying — while the padding is still **added** on top of it. Measured: masthead ink and content aligned exactly at 1440 and sat 35px apart at 2300, on a value chosen so they would match. **Compute both sides the same way, or the agreement is a coincidence of viewport.** The same choice also decides where an absolutely-positioned child lands: `right: 0` resolves against the **padding box**, so a padded measure hangs a control outside its own ink.

- **⚠️ A MOCKUP ONLY EXERCISES THE GLYPHS SOMEONE TYPED INTO IT.** *(21 Aug, the masthead title.)* Descenders, diacritics and long strings are exactly what a ref does not test — its author writes a plausible label, it looks right, and the value tuned to it ships. `line-height: 1.02` came from TWO refs that agreed, and **two artefacts agreeing is not corroboration when they share a blind spot**: both drew titles with no descenders, so neither could show that the largest text on every page was being cropped. It reached dev.
  - **THE COROLLARY FOR VALUES READ OFF A REF:** a number tuned to the sample renders the sample correctly. ### From “Conventions & invariants” (CLAUDE.md lines 710–714)

- **⚠️ `line-height: 1` IS ONLY EVER SAFE ON UPPERCASE-ONLY TEXT — ON MIXED-CASE PLAYFAIR IT CUTS THE DESCENDERS.** *(21 Aug. A correct rule applied to the wrong type, which is why it survived review three times.)* `line-height: 1` was RIGHT for the retired mono-uppercase band label: uppercase mono has no descenders, so a line box the size of the em is exactly the ink. The same declaration on Playfair rendering mixed case crops the `y` in "ScriptAlly" and in "Query Centre". **Minimum 1.3 anywhere Playfair renders mixed case**; a fixed height with `overflow: hidden` does the same damage by a different route, so **size a text container by its line box, never by a number that happens to fit most glyphs** — `min-height` plus padding where a row needs a nominal height.
  - **MEASURED ON DEV, THREE SITES:** the sidebar brand `.ws-bwm` (26px of ink in a 22px box), the masthead title `.wsh-title` (35 in 31, at 1.02× — a value taken from two refs whose drawn titles happened to have no descenders), and the folded bar `.wpg-mini-name` (22 in 19).
  - **⚠️ THE CHECK IS `scrollHeight === clientHeight` ONLY WHERE THE BOX ACTUALLY CLIPS — OTHERWISE IT IS THE WRONG INSTRUMENT, AND IT HAS NOW MISLED TWO PASSES.** On an `overflow: visible` box `scrollHeight` reports the union of the content box and anything spilling out of it, and **Playfair's ascent plus descent exceed any `line-height` under ~1.15** — so a sweep written that way reports *every* tight-leading Playfair element on the marketing pages as cropped while nothing is cropped at all. Measured 24 Aug: 18 "failures" on the landing, **zero real**. The reading only means "crops its OWN content" when the element has `overflow: hidden`/`clip` or a fixed height. **The instrument that is always right is INK against a CLIPPING ANCESTOR**: take the union of the element's `Range.getClientRects()`, walk up for the first ancestor whose `overflow` is not visible, and ask whether the ink is outside its box. Do both where the box really clips, and **collect every offender rather than throwing at the first** — this kind of declaration gets copied, and the pack that named two sites had three. ⚠️ **AND KEEP THE `line-height < 1.3` READING AS A CENSUS, NEVER AS A FAILURE.** Seven marketing elements sit below the floor on purpose and each was measured (`mk-wordmark` 1.00, `mk-mission-main` 1.02, `mk-dn` 1.10, `H2` 1.18/1.20, `mk-turn-b` 1.22, `H3` 1.25). Printing the set and comparing it to the known one catches a NEW offender without going red on the sanctioned ones.
  - **⚠️ AND THE PROBE MUST SAMPLE A STRING THAT HAS A DESCENDER.** "Dashboard" has none and passes on a clipped box; "Query Centre" does not. The ratio check exists for the same reason: a box that does not clip TODAY because of the words in it will clip the day the page is renamed.
  - **⚠️ A SYMPTOM REPORT NAMES A PLACE, NOT AN ELEMENT.** This arrived as "the top breadcrumb bar — ScriptAlly and the page name, both clipped". The breadcrumb runs at 1.5× and is whole; the clipped "ScriptAlly" is the SIDEBAR wordmark sitting in the same band. **Scan for the property, do not grep for the described class** — a probe list written from the description would have fixed a page that was not broken.

### From “Conventions & invariants” (CLAUDE.md lines 719–730)

- **⚠️ ON A PAGE WHERE NOTHING SCROLLS, `position: sticky` DOES NOT IDLE — IT CLAMPS.** *(20 Aug, the mini bar's `top` offset.)* Everyone holds sticky as "it pins the element when it would otherwise scroll away"; what it actually does is **clamp the element into the region at or below its `top`**. Those are the same thing on a scrolling page and they are not the same thing on a fill page, where there is no scrolling and the clamp is the ONLY behaviour left. Giving the control row `top: 51px` — to clear the mini bar above it — therefore pushed the row DOWN 51px on every fill page, where no mini bar renders. **The signature is a fold that reclaims less than it should:** Calendar's masthead collapsed 118px and the content below it rose 67, the missing 51 being a gap held open for an element that was not there.
  - **⚠️ `top: 0` HIDES THIS RATHER THAN FIXING IT** — clamping to 0 is a no-op when the natural position is already 0, which is why the row carried a sticky nobody noticed for two packs. The honest statement is `position: static`: a sticky on a page that cannot scroll claims a behaviour that cannot occur, and **a dead claim is how the next reader is misled** into adding an offset to it.
- **⚠️ SCROLL ANCHORING IS A BROWSER BEHAVIOUR THIS APP NOW DEPENDS ON — `overflow-anchor: none` IS NOT A FREE FIX.** *(20 Aug, the mini bar.)* The bar takes its full height in FLOW the moment a page sticks (42.7px since the height started deriving from its type — it was 51), so everything below it moves down and `scrollHeight` grows by the same. Nothing lurches only because the browser raises `scrollTop` by the identical amount: measured on Contact list, a 10px wheel tick takes `scrollTop` 0 → 53 and a content landmark moves exactly 10px. **Adding `overflow-anchor: none` anywhere on an ancestor of `.wpg-scroll` — a common reach when chasing an unrelated flicker — makes content lurch half a bar-height down on the first tick of every scrolling page, and it reads as a mini-bar bug.** `stickyRow.measure.ts` fails first and names the cause; the stylesheet carries the warning where the `none` would be typed.
  - **AND IT IS SINGLE-ENGINE EVIDENCE.** Chrome and Firefox anchor; Safari's behaviour differs; the harness only ever asks Chromium. The measurement proves the property where it is taken and not that it holds everywhere — the honest reading of any one-engine result, and worth remembering before it is quoted as settled.
- **⚠️ `position: sticky` INSIDE A GRID NEEDS ITS TRACK TO STRETCH, OR IT HAS NOWHERE TO TRAVEL — AND IT FAILS SILENTLY.** *(28 Aug, the packages builder's New-package panel. Third member of the same family: the declaration is valid, it matches, the browser honours it, and the thing you wanted does not happen.)* A sticky element can only move inside its **containing block**. `align-items: start` on the grid collapses every track to its own content, so a panel that is the only thing in its track gets a track exactly its own height and **zero range**. Measured: `position` computed `sticky`, `top` computed the correct `71.6px`, and the panel scrolled clean off the top of the screen at `-6.1`.
  - **THE FIX IS PER-ITEM, NEVER THE CONTAINER.** `align-self: stretch` on the one column that needs it — because `start` is right for the other column, whose cards must not stretch. Setting the container to `stretch` "to fix the sticky" is the second bug wearing the first one's clothes, and this file already records the same shape on the marketing hero's grid.
  - **THE TELL IS A SIBLING THAT IS SHORTER THAN THE ROW.** If the sticky element's column holds only the sticky element, the track is its height and sticky is decorative. **Assert the RENDERED top against the thing it must clear**, never `getComputedStyle().position` — the computed value is right in both worlds, which is exactly why this survives review.
- **A sticky child of a scroller is one application of the viewport law above — it caps itself to the SCROLLPORT.** `--wpg-port-h` and `--wpg-stuck-h` are what it reads; the reasoning, the evidence and the sentinel rule all live in that one entry rather than being restated here.
- **⚠️ A DECLARATION CAN APPLY CLEANLY AND HAVE NO EFFECT — AND COLLAPSING MARGINS ARE THE CHEAPEST WAY TO GET THERE.** *(20 Aug, the in-flow masthead's sticky control row. Same family as `transform` isolating a `mix-blend-mode` group: the rule is valid, it matches, the browser honours it, and the thing you wanted does not happen.)* The sticky row tightens its padding when it anchors, which takes 4px out of its flow height and therefore out of `scrollHeight` — the shrink/clamp/un-shrink cycle documented under the header rules. The compensation was written as **`margin-bottom: 4px`**, which is exactly right in arithmetic and worth nothing in practice: **adjacent siblings' margins COLLAPSE**, so it was absorbed by the following element's `margin-top` and the row's contribution fell by 4 anyway. **`padding` cannot collapse; `margin` can.** Any compensation that has to preserve a box's contribution to a scroll height must be padding, a border, or a rule inside a flex/grid container, where collapsing does not happen at all.
  - **⚠️ IT IS INVISIBLE TO EVERY SOURCE-READING CHECK, AND THE UNIT LOCK PASSED.** The lock summed `2 × padding + margin-bottom` off the stylesheet and got 24 = 24 — correct arithmetic about a page the browser does not lay out that way. **A compensation is verified by measuring the box, never by adding up its declarations.**
  - **⚠️ AND IT HID BEHIND A BIGGER FAULT.** A stale `--wpg-reclaim-pad` was adding 99px in the same state change, so the −4 was invisible until that was removed. **When one measurement is wrong by a large number, fix it and MEASURE AGAIN before concluding anything about the small ones** — the second reading is where the subtle fault lives.
- **⚠️ MOTION TRAP — a card sits ~7px out of place after a reflow, looking like a layout bug.** *(Stated symptom-first on purpose: the symptom points away from the cause, so anyone hitting this will chase it through layout code first and find nothing wrong there.)* **Cause:** an entrance animation with `fill-mode: both` outranks inline transforms, so a FLIP offset is discarded and the keyframe's own offset wins instead — `transform: translate(200px,150px)` on a card holding a finished `rise` computes to `matrix(1,0,0,1,0,7)` (browser-measured, 29 Jul). It is not "the transform is ignored": the element is actively displaced by the animation's `from` value, silently and with no error. **Fix:** settle every participating element (`animation: none` — the shared `.sa-settled` class in `src/styles/motion.css`, which carries `!important` because it must beat the shorthand that set the animation running) BEFORE any position is measured, and settle them all before measuring any of them, since adding a class can itself reflow. Applies to every FLIP anywhere in the app, not just the agent list.
