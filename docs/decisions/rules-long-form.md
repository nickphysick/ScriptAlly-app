## (part of “Working discipline (READ FIRST — repo hygiene rules, locked 8 Jul; supersedes the old "Multi-stream protocol" model)”)

- **One active session per working tree.** Never run two sessions in the same checkout. For genuinely parallel work, each session gets its OWN worktree: `git worktree add ../ScriptAlly-<task> main`. Clean up worktrees when done (`git worktree remove`); end state is normally just the primary tree `/Users/nickphysick/ScriptAlly-app`.
  - **⚠️ EVERY WORKTREE IS ~1.2 GB (reports + design-refs are tracked), AND ABANDONED ONES FILLED NICK'S DISK.** *(19 Oct: 43 worktrees, 40 GB, laptop full.)* So:
    - **The session that creates a worktree removes it before it ends.** Once the branch is committed and pushed, run `git worktree remove <path>`. The branch survives, so a worktree can be recreated in seconds. The wrap-up recap says the worktree is gone, or names it and gives the reason it was kept.
    - **Measurement, integration, deploy and "-base"/"-gate"/"-int" worktrees are disposable by definition.** Remove them at the end of the run that made them. Put deploy checkouts in the scratchpad.
    - **Before `git worktree add`, run `git worktree list`.** If more than 5 worktrees exist besides the primary, tell Nick and offer to clean up the clean ones first.
    - **Never remove a worktree with uncommitted edits.** For a clean worktree with untracked files, first copy the strays to `~/ScriptAlly-backups/worktree-strays-<date>/<name>/`, then run `git worktree remove --force`, then `git worktree prune`.
    - **Never add a second `node_modules`.** Symlink the primary's, as the measurement-worktree rule already says.
- **⚠️ AND READ `git log` BEFORE STARTING A PHASE — A HAND-OFF IS A CLAIM ABOUT THE REPO, NOT THE REPO.** *(27 Aug.)* A summary handed over at "Phase 3 — go" was stale: Phase 3 had already been done and committed. The whole phase was rebuilt from scratch before `git add` staged nothing and gave it away. **The redo came out byte-identical, which is reassuring about determinism and no consolation for the cycle.** One `git log --oneline -8` at the top of a phase answers "has this already landed", and it is the same class as the level-with-`main` check below: everything a phase concludes is wrong if its starting point is.
- **⚠️ STEP 0, BEFORE ANY RECON: confirm the worktree is LEVEL WITH `main`** (`git rev-list --count HEAD..main` = 0). This has bitten twice — most recently a shell rebuild whose recon ran against a base **40 commits stale**, which would have produced conflicts in every file it touched. It is a one-line check and it belongs ahead of reading any code, because everything recon concludes is wrong if the base is.
- **Before any task:** confirm `HEAD` is on `main` and the tree is clean. If it isn't, STOP and report — do not proceed on top of unexplained dirt. Never `git switch` / `git stash` / `git checkout --` / `git restore` / `git clean` a checkout another session may be holding.
  - **⚠️ `git commit --amend` BELONGS ON THAT FORBIDDEN LIST, AND IT IS THE ONE EXPLICIT-PATH STAGING DOES NOT PROTECT.** *(27 Aug, done rather than theorised.)* `--amend` rewrites whatever commit is at **HEAD**, and in a shared checkout HEAD is whoever committed last. A tsc slip was found seconds after committing; the other session committed in that window; `git commit --amend --only -- <my paths>` therefore **rewrote THEIR commit**, folding a four-line fix of mine into it. Nothing was lost — an amend preserves the original tree, and nothing had been pushed — but their commit now contains a file they never touched, and had it been pushed the rewrite would have been published. **`--only` scopes the CONTENT and does nothing about the TARGET.** The fix for a slip in your own commit is a new commit; a tidy history is not worth a ref another session is standing on. And rewriting again to undo it is worse than leaving it: report it and move on.
  - **⚠️ AND HERE IS WHAT TO DO INSTEAD, BECAUSE THE PROHIBITION ALONE IS BROKEN UNDER PRESSURE.** The moment it gets broken is always the same: a red gate, and a plausible-looking way to isolate it — *"I'll just stash their files, confirm the red is theirs, and put it back."* That is the exact shape of a near-miss recorded on 26 Aug: the stash and pop both succeeded and nothing was lost, but a conflict, or the other session writing inside that window, would have destroyed uncommitted work belonging to somebody else. **The near-miss is the finding, not the outcome.**
  - **TO ESTABLISH PROVENANCE OF A RED, READ — DO NOT MOVE.** `git status --short -- src/` names whose files are dirty; the failing test's own imports name what it exercises. If it imports nothing you have touched, it is not yours, and you have proved it without moving a byte. Two commands, no risk, and it works while the other session is still typing.
- **Stage by explicit path** (`git add <path>` then `git commit --only -- <paths>`); never `git add .` / `git add -A`. `git diff --cached --name-only` should list only the paths you intend. Gates green (tsc + production build + full Vitest, with `set -o pipefail`) before every commit.
- **⚠️ THE BUILD'S OUTPUT IS READ IN FULL, OR GREPPED — NEVER BY `tail` ALONE, AND A GREEN EXIT CODE IS NOT A CLEAN BUILD.** `vite build` prints CSS diagnostics near the TOP and exits 0 anyway, because they are warnings. Measured 18 Aug: a `css-syntax-error` from a malformed comment sat at **line 7 of 185** while every gate reading in this repo takes the last few lines — so it was printed on every single build for as long as the damage existed, and no gate could ever have failed on it. The browser was discarding a whole rule the entire time. Use `npx vite build 2>&1 | grep -inE "error|\[WARNING\]"` (the chunk-size note is the one expected match) or read the whole log; `tail -4` is how this hid.
- **⚠️ AND THE INVERSE ON THE TEST GATE: `npx vitest run` CAN EXIT 1 WITH ZERO FAILED TESTS.** *(9 Sep, seen three times in one session, always with other node processes on the box — this machine routinely runs several sessions' `vite preview` servers at once.)* The run ends `Errors 1 error` and a non-zero exit while every test passes:
  ```
  ⎯⎯⎯⎯⎯⎯ Unhandled Errors ⎯⎯⎯⎯⎯⎯
  Error: [vitest-worker]: Timeout calling "onTaskUpdate"
  ```
  That is the REPORTER's RPC channel timing out under CPU load, counted as an unhandled error — not a test failure and not a fault in the tree. Measured the same run: `465 passed (465)` files, `7698 passed | 3 skipped`. **A gate reading only the exit code calls that a red build**, and the honest reading is the same one the build gate needs from the other direction: read the COUNTS, not the status line. The tell is `Errors  N error` with no `FAIL` lines and no failed-test tally; a real red always names the file and the case. It travels with a slow run — 130s to 278s against a normal 27–40s, with `collect` inflated four to twenty times.
- **⚠️ NEVER PIPE A GATE INTO ANYTHING BEFORE READING ITS EXIT CODE — `set -o pipefail`, then read `$?`.** *(10 Sep.)* `npx tsc --noEmit 2>&1 | tail -3 && echo "TSC CLEAN"` printed **CLEAN over three real TS2554 errors**: `tail` always exits 0, so the `&&` fires whatever the compiler said. This is the `tail -3` rule above meeting "a green exit is not a clean build" from the other direction, and **the dangerous half is not the three errors — it is that the word CLEAN was being produced by the FORMATTER rather than by the compiler.** Any gate whose verdict is echoed by a following command must carry `set -o pipefail`, or the verdict belongs to the last process in the pipe.

- **⚠️ AND READ THE OUTPUT BEFORE YOU COMMIT — A RED PRINTED ABOVE THE COMMIT LINE IS STILL A RED.** *(10 Sep.)* A scoped suite failed, the failure printed, and the commit ran in the same block seconds later because nothing made it stop. This is the sibling of the `git status`-after rule and fails the same way: the evidence was on screen and unread. **Chain the gate to the commit (`&&`), or read the counts and commit as a separate act** — never put a gate and a commit in one block where the commit runs regardless. The repair is a follow-up commit, and the first one stays on the record.

## (part of “Working discipline (READ FIRST — repo hygiene rules, locked 8 Jul; supersedes the old "Multi-stream protocol" model)”)

- **⚠️ `git commit --only -- $(git diff --cached --name-only)` DROPS THE DELETE HALF OF EVERY RENAME.** *(30 Aug, and it left a superseded lock file on `main` inside the very commit that documented why a replacement must be SWAPPED rather than ADDED.)* For a rename `git diff --cached --name-only` prints the NEW path only; `--only` then scopes the commit to the paths listed, so the create lands and the delete stays staged. The result is both files tracked — the old one still collected by the runner, still asserting the mechanism the commit deleted.
  - **THE TELL IS `git status` AFTER THE COMMIT.** A lone `D  <old path>` still staged is exactly this, and it is why the clean-tree check belongs AFTER the commit as well as before it. Use `git diff --cached --name-status` and take BOTH sides of any `R`, or check the tree with `git ls-tree --name-only HEAD <dir>` when a rename is in the change set.
- **⚠️ AFTER STAGING, `git status` MUST SHOW A CLEAN TREE BEFORE THE GATES ARE BELIEVED.** Explicit-path staging is the right rule and this is its cost: it will silently omit a file you changed *for the very reason you are committing*. If anything is still modified, the suite you just ran was run against a tree the commit does not contain — so "green locally" proves nothing about what you pushed. This is not hypothetical: on 6 Aug a retargeted lock in `src/lib/` was left behind by a commit that staged `src/components/todo/`, the local suite was green, and CI — which only ever sees what was pushed — was right where I was not.
- **⚠️ INITIALISATION CALLS GO AT THE END OF A MODULE, never at the foot of a block that a later block extends.** A `var`-hoisted table read by an earlier init call is `undefined` at that moment, and the throw silently kills every later initialiser — so the failure surfaces as unrelated features going quiet rather than as an error anyone can trace back. The same shape catches `const` in a module's temporal dead zone, and **`tsc` only sees it when the reference shares the declaration's scope**: read the same `const` from a helper the render calls and it typechecks clean (see the TDZ note above). Comments are not guards here either — **assert the initial render state in a test**, because a module that throws on load renders nothing and a source-string suite will not notice.
- **⚠️ COMMENTS ARE NOT GUARDS. A constraint worth a warning comment is worth a test.** A `⚠️` in a file is a note to whoever happens to read that line; it stops nothing. Also on 6 Aug, `ToDoPage.tsx` carried a verbatim warning against declaring a post-return `const` that the render reads — and the bug was written into that same file, in a session that had read the comment, and shipped to dev as a page that would not load through a fully green suite. If you find yourself writing "⚠️ never do X here", write the assertion that fails when someone does; the comment then explains the test rather than standing in for it.
- **⚠️ A NEW ROUTED PAGE SHIPS WITH A SMOKE TEST FROM DAY ONE.** One entry in `src/test/pageSmoke.tsx`'s census, one file asserting the page renders + one distinctive chrome string — the pattern in `dashboardPageSmoke.test.tsx` and its siblings. **This repo's tests read SOURCE** (`vitest.config.ts` is `environment: 'node'`; no jsdom, no testing-library), and a source-string test cannot see a runtime crash: it proves the code was written, not that it ran. Keep the assertions minimal — a smoke that pins appearance becomes the next false red. **Smoke the POPULATED state too wherever the page branches to a first-run panel**, or every derivation on it stays unexecuted. Full inventory + rationale: `reports/app-smoke.md`.
- **⚠️ `tsc` DOES NOT CATCH THE TDZ BUG — do not assume a green typecheck covers it.** Used-before-declaration (TS2448) fires only when the reference shares a scope with the declaration. The shape that actually shipped read the `const` from inside a **hoisted helper the render calls**, which TypeScript treats as legal because it cannot know the helper runs during render. A direct `description={helper()}` in the JSX *is* caught by tsc — so **testing a guard against that shape proves nothing**. Verified 6 Aug: the real shape reintroduced into `AllManuscripts.tsx` passed tsc AND the production build, and was caught only by the render smoke and `pageStructure.test.ts`.
  - **⚠️ THE THIRD SHAPE IS AN IIFE, AND BEING CAUGHT BY TS2448 IS WHAT MAKES YOU MISS IT (26 Aug).** A `const` whose initialiser is an immediately-invoked arrow runs **at its declaration**, so a read of any `const` below it is a TDZ — and `tsc` cannot see through the IIFE any more than through a hoisted helper. The journey round hit BOTH halves in one session: `closeReason` reading `activeFlow` from the same scope was correctly refused with TS2448, one declaration was moved, and the shape was treated as closed. It was not — `paneWill`'s IIFE read the same two `const`s from two hundred lines above them, compiled clean, passed **6,995 unit tests** and a clean production build, and threw `Cannot access 'Rr' before initialization` inside `useTaskPaneSession` on every render with a docked card. **The whole To-do page fell into its error boundary the moment a task was opened, and it reached `main` that way.** So: **TS2448 is a signal to audit every render-time read in that function, never a sign the problem is handled** — and the rule to apply is the ORDER (anything a render-time expression reads is declared above it), which is lockable as `indexOf(dep) < indexOf(consumer)` with BOTH halves asserted, since an ordering lock over a consumer that stopped reading its dependencies passes forever.
- **PROD deploys are Nick's only — never Claude.** Claude Code never runs `firebase deploy` against **prod** (hosting, functions, or rules — i.e. `firebase.json` / `firebase.holding.json`). **DEV deploys are fine whenever Nick asks:** `npm run build:dev && firebase deploy --only hosting --config firebase.dev.json --project dev` (hosting-only unless functions/rules changed). (Clarified 14 Jul — supersedes the earlier blanket "no deploys" line, which contradicted the long-standing dev-on-request workflow.) **⚠️ AMENDED 18 Aug: dev FIRESTORE RULES no longer need asking — see the Deployment section, which owns the command and its before/after checks.**

## Disk hygiene — emulator runs filled the disk (6 Nov; one worktree's debug logs reached 38 GB)
- **Every emulator run goes through `scripts/emu-guard.mjs`**: `npm run e2e:emu` / `dev:emu` / `emu:seed` / `test:rules` / `test:functions` all do. **Never call `firebase emulators:*` directly** (`src/test/emuGuard.test.ts` fails on one). The guard refuses to start under 20 GB free (`EMU_MIN_FREE_GB`), points every `*-debug.log` at `/dev/null`, kills the run under 10 GB free, and removes the logs and `dist-emu/` on exit. To read a log, use `EMU_DEBUG_LOG=1` (deleted on exit) or `EMU_DEBUG_LOG=<absolute dir>` (kept there). Either way a log over 200 MB (`EMU_MAX_LOG_MB`) kills the run.
- **Never run a test suite in a loop or an unattended repeat.** One run, read the result, act.
- **Step 0 of every session: `df -h ~`. STOP if under 20 GB free.**
- **End of every session that made a worktree:** first commit, or list in the report, any uncommitted work (`git status --short` empty or accounted for). Then `git worktree remove` your own worktree and delete its `node_modules`, `dist-emu` and emulator data. Never force-remove a worktree with uncommitted `src/`, `functions/` or `design-refs/` changes.
- **Never touch another session's worktree**, its emulators or its ports.

## Deployment
- **`/Users/nickphysick/ScriptAlly-live` is the only prod deploy folder.**
- **Prod only ever ships the pushed tip of `release/live-1`** (preflight check 4c fails on anything unpushed, behind or detached).
- **Small landing changes: commit on `release/live-1`, push, then `npm run deploy:live-hosting` (Nick's to run).**
- **Never deploy prod from a scratch worktree.**
- **Dev can carry several unmerged branches at once. Before any dev deploy, name the branch the served bundle was built from. If it isn't the branch you're on, merge yours into it as a new branch and deploy that. A bundle-hash mismatch is a stop.**
- **⚠️ DEV FIRESTORE RULES ARE CLAUDE'S TO DEPLOY (18 Aug). PROD REMAINS NICK'S — hosting, functions and rules alike.** The whole of the dev rules deploy is ONE command, and it names its config and its project because a bare deploy resolves `.firebaserc`'s default, which is PROD:
  ```
  firebase deploy --only firestore:rules --config firebase.dev.json --project scriptally-dev
  ```
  **NEVER prod, and never hosting as part of a rules deploy** — they are separate acts with separate blast radii.
  - **BEFORE:** `grep` `firestore.rules` for the fields the deploy is meant to carry and report which are present. **If any is missing from the working tree, STOP — the tree is wrong, not the deploy.**
  - **AFTER:** verify by release `updateTime` under `--debug`, **never the success line** (which never names the database), then run `node tests/e2e/rulesProbe.mjs` and report the vintage.
  - **⚠️ WAIT BEFORE PROBING — RULES TAKE SECONDS TO PROPAGATE, AND AN IMPATIENT PROBE REPORTS A FALSE DENIAL.** Measured 18 Aug: seconds after a deploy whose uploaded source demonstrably contained the field, one new field read DENIED while another new field from the *same release* read ACCEPTED; a minute later both were accepted. That asymmetry is the tell, and it is a nasty one — it looks exactly like a rule that was written wrong, and it survived a check of the uploaded ruleset source. **If a probe denies something the uploaded source contains, wait and re-run before believing it.**
- **⚠️ `rulesProbe.mjs` RETURNS A VINTAGE, NOT A YES/NO — use it instead of inferring from a denial.** A permission error cannot distinguish "not deployed" from "deployed to the other database" from "one field missing" from "the document is invalid for an unrelated reason", and those have four different fixes. The probe signs in as the harness user and attempts one field at a time, each labelled with the commit it arrived in, undoing every write — so the answer is *which commit the deployed ruleset stops at*. It found the real cause twice in one day: once a deploy that simply predated the commit it was expected to carry, and once a denial that had nothing to do with rules at all (see below).
- **⚠️ A DENIAL CAN BE ABOUT THE DOCUMENT ID, AND `isValidId` IS EASY TO FAIL BY ACCIDENT.** It requires `^[a-zA-Z0-9_-]+$`. Any id BUILT FROM DISPLAY TEXT can break it: the backfill's heal id is composed from the query's STATUS, and `Revise & Resubmit` contains an ampersand — so the heal for every R&R query was denied permanently and silently, with one console line as the only trace. **Sanitise any generated id to that charset at the point of construction**, and when a write is denied, check the id before assuming the rules are stale.
- **⚠️ EVERY `firebase deploy` NAMES ITS TARGET. A BARE DEPLOY IS FORBIDDEN.** Always pass `--project` explicitly — `--project scriptally-dev` (or the `dev` alias) for dev, the `prod` alias for prod. Without it the CLI resolves `.firebaserc`'s **`default`, which is `gen-lang-client-0801391782` — PROD**. So `firebase deploy --only firestore:rules`, typed in a session whose every other line says "dev", deploys to production. This is not hypothetical: an instruction to deploy dev rules was written exactly that way (6 Aug) and would have hit prod had the target not been checked first. The rule is mechanical because the failure is silent — nothing in the command reads as dangerous.
- **⚠️ THE DEPLOY SOURCE IS A CLEAN CHECKOUT OF THE PUSHED TIP, NEVER THE WORKING TREE.** *(4 Sep.)* The working tree contains whatever every other session has half-done — a build there ships it. Checked out the tip in a detached worktree, built, deployed, and confirmed the served bundle hash against that build; the primary tree at the time held another session's uncommitted Calendar rebuild, which a routine `npm run build:dev && firebase deploy` would have put on dev under a commit message about page headers.
  - **IT IS THE SAME SHAPE THAT PUT A STALE LOCK ON DEV**, and the general form is: *the thing you deploy must be the thing you pushed, and only a clean checkout can promise that.* One `git status --short` in the source directory before the build is the whole check.

## (part of “Deployment”)

- **⚠️ `cd X && …` IS NOT A GUARD — A FAILED `git worktree add` LEAVES THE DEPLOY RUNNING IN THE SHARED TREE.** *(4 Sep, done rather than theorised, and the standing "deploy from a clean worktree" rule was defeated by shell semantics rather than by forgetting it.)* `git worktree add` refused a path with a **stale registration** (`use 'add -f' to override, or 'prune'`), so the following `cd /tmp/sa-dep` failed too — and every remaining command in the compound ran **in the primary checkout**, including `npm run build:dev` and `firebase deploy`. The deploy succeeded, reported success, and shipped the shared tree.
  - **IT COST NOTHING ONLY BY LUCK, AND THE LUCK IS THE POINT.** `git status --short -- src/` was empty at that moment, so no other session's uncommitted work went out. Had anyone been mid-edit it would have been deployed under a commit message about tasks and behaviours — which is the exact incident the clean-worktree rule exists to prevent, arriving through a door the rule does not cover.
  - **AND MAIN HAD MOVED**, so the build was of another session's tip rather than the commit intended. Nothing was lost (the intended commit was an ancestor), but the deploy published work its author had not asked to publish.
  - **THE FIX IS `set -e` PLUS AN EXPLICIT STOP: `cd /tmp/wt || { echo "STOP"; exit 1; }`**, and a `git worktree prune` before `add`. A `test -z "$(git status --porcelain)" || exit 1` after the `cd` then proves the gate ran **in the directory you think it did** — the check is worthless if it can pass in the wrong tree.
- **⚠️ A FAILED DEPLOY CHECK IS A STOP. PROVING AFTERWARDS THAT IT DID NOT MATTER IS A GOOD ANSWER TO THE WRONG QUESTION.** *(28 Aug.)* The clean-tree check flagged an untracked stray and the deploy went ahead anyway; the stray was then shown to be unimported and the rebuild came out byte-identical, so the deploy was sound. **The deploy being sound is not the point** — the gate exists so that nobody has to reason about it, and a gate you reason past is a gate you have removed. Fix the tree, re-run the check, then deploy.

## Conventions & invariants
- **⚠️ AN EDIT THAT CHANGES A VALUE READ ELSEWHERE MUST SAY WHAT IT CHANGES, COMPUTED BY A DRY RUN THROUGH THE REAL CODE, BEFORE IT IS SAVED.** *(Contact list v11, 25 Sep — the Also-changes engine, and now a law because the alternative was measured.)* A note that DESCRIBES the consequence from arithmetic (`stage date + weeks × 7`) is a confident wrong value waiting for the first record the shortcut does not fit: on a writer-dated query the engine's recency law holds the writer's own date whatever the agency window becomes, and the shortcut moves it. ## (part of “Conventions & invariants”)

- **⚠️ AN ESCAPE CASCADE IS ONE HANDLER, NOT TWO LISTENERS.** *(24 Sep.)* Two capture-phase `keydown` listeners on `document` are resolved by REGISTRATION ORDER — a fact about which element mounted last, not about what is on screen — so "the popover consumes the key and the card does not" holds or fails depending on render order. **The outer surface owns the key and asks whether the inner one is open first** (`if (menuRef.current) { setMenu(null); return; }`), which is the cascade this file already states in prose for the agent card and the only form that a mount cannot reorder. It also means the inner control needs no Escape handling at all, which is what a lock can assert.
- **⚠️ AN UNDO THAT RESTORES NOTHING IS WORSE THAN NO UNDO — AND IT IS ONE EMPTY CLOSURE AWAY.** *(20 Aug, the correction sheet's removal.)* `showToast({ message, undo })` renders the UNDO button whenever `undo` is present; the first wiring passed `async () => {}`, so the writer would have removed two entries, pressed Undo, and been told it was reversed while nothing moved — silently, with no error, and with the toast already spent. **An absent control leaves someone knowing they must fix it themselves; a dead one leaves them believing it is already fixed.** The ToastProvider's own docstring states the rule (*"reversible action → `showToast({ message, undo })`"*), and nothing enforces it: a no-op satisfies the type.
  - **THE INVERSE MUST CAPTURE BEFORE IT DESTROYS.** "Restore by id" is only possible while something still holds the contents — after the delete there is nowhere to read them from. `deleteActivities(ids)` reads both stores, deletes, and returns the closure that writes them back.
  - **⚠️ AND BOTH STORES TRAVEL TOGETHER, WITH ONE RECOMPUTE AT THE END.** An entry is a projection in the global feed and a document in the query's own log; restoring one leaves the two disagreeing, and a recompute run between two restores derives from a half-restored log and writes a status the writer never had.
  - **⚠️ THE LABEL IS `.toUpperCase()`d, WHICH DEFEATS A CASE-SENSITIVE PROBE.** A measurement looking for `/^Undo$/` reported "no undo was offered" about a button that was on screen — the wiring fault it was written to catch, wearing the same face. Reconcile the send set against `sendSpecFor` — **two derivations against each other**, never against a hand-written list on both sides.
  - **A SECOND MECHANISM IS NOT A FIX.** An offer card drew a tick for months; the write was prevented only because `quickDone` re-checks `getPrimaryAction(q.status).kind`. The map said yes and something downstream said no — which the module's own docstring already calls out: *"a tick that does nothing is worse than no tick"*.
- **⚠️ IF THE UI OFFERS A CHOICE THE TYPE CANNOT REPRESENT, THE TYPE IS WRONG — never map an unrepresentable choice to its nearest neighbour.** *(21 Aug.)* `RemindChoice` was `{kind:"lead",days} | {kind:"none"}`, and the form offered "A custom date…". - **⚠️ EVERY WORKSPACE PAGE STAYS MOUNTED, SO A HARD-CODED `id` IS A DUPLICATE THE MOMENT A SECOND SURFACE RENDERS THE SAME COMPONENT.** *(23 Aug — recorded as a GENERAL hazard on Nick's instruction, after the third session it has bitten. Its intended home is the harness pack's flag 4; this is the standing record until that report exists.)* The known half of this trap is that `document.querySelector` can return a **hidden page's zero-sized copy** — which has produced a false finding, a seven-minute `locator.hover` hang, and an "unclickable" button hunt. **The half that is new is the id.** `TaskPaneBody` renders `id="s-unit"`, `id="s-when"`, `id="s-expect"`, `id="s-remind"`; mount that component on a second page while the first is alive and the document holds **two of each**. Two consequences, and the first is the one that looks like a feature bug: `document.querySelector('.tpn #s-unit')` returns the FIRST match, so a "jump to the missing answer" scrolls a page the writer cannot see; and duplicate ids are invalid HTML, so any `aria-labelledby` or label-`for` resolving by id becomes ambiguous. **Scoping the query to a ref fixes the first and NOT the second** — the ids are still duplicated, and the fix for that is an `idPrefix` prop defaulting to today's values so the original page stays byte-identical. **The rule: before a component with a hard-coded `id` gains a second mount, give it an id prefix.** Grep for `id="` in any component about to be reused, and remember that in this app "reused" means "rendered on two routes", which is the normal case rather than the exotic one.
- **⚠️ A COMMIT MESSAGE STATES WHAT ITS DIFF DOES.
