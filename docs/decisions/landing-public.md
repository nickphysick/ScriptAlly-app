### From “Deployment” (CLAUDE.md lines 582–601)

- **⚠️ `/api/waitlist` IS ROUTED ON DEV AND DELIBERATELY NOT IN `firebase.json`. DO NOT "FIX" THAT.** A rewrite in prod's config is only correct *after* the function exists in prod — and until then the next prod hosting deploy, for any reason, by anyone, silently points `/api/waitlist` at a function that is not there. Hosting 404s it, **the SPA catch-all turns the 404 into `200 text/html`**, and the client is handed its own index page where it asked for JSON. That is a failure that looks like a success, and it is the exact shape `src/marketing/waitlist.ts` checks `content-type` to survive. **A config line that is only correct after a deploy that has not happened is a trap sitting in the repo.**
  - **THE BLOCK TO PASTE INTO `firebase.json`'s `hosting.rewrites`, WHEN THE TIME COMES — FIRST IN THE ARRAY, ABOVE THE CATCH-ALL.** Firebase takes the FIRST matching rewrite, so `**` placed above it swallows the API path. And the **region must be pinned**: functions here are v2 in `europe-west2`, and the short `"function": "waitlist"` form looks up a DEFAULT-region function, finds nothing, and produces exactly the silent-HTML failure above.
    ```json
    { "source": "/api/waitlist",
      "function": { "functionId": "waitlist", "region": "europe-west2" } },
    { "source": "/api/waitlist/**",
      "function": { "functionId": "waitlist", "region": "europe-west2" } }
    ```
    **⚠️ BOTH ENTRIES, AND THE SECOND IS NOT OPTIONAL.** A hosting `source` is a GLOB, not a prefix: `/api/waitlist` matches that one path and nothing beneath it. With only the first entry the endpoint answers and **`/api/waitlist/verify` and `/api/waitlist/unsubscribe` fall through to the SPA catch-all as `200 text/html`** — so every verify link in every founding invite lands on the marketing page and silently does nothing. Measured on dev on 26 Aug, with the function correctly deployed: the bare path returned JSON and both sub-paths returned the app's own index. **The endpoint working is not evidence the links work.**
  - **⚠️ THE ORDER IS FUNCTION → RULES → HOSTING, AND BACKWARDS IS THE FAILURE.** Hosting first publishes a rewrite pointing at nothing, so every request in the window between the two deploys gets `200 text/html`; the counter silently vanishes and a sign-up silently fails as `down`. Function first means the endpoint answers before anything points at it — harmless. Rules go in the middle because they only ever *tighten* access to `waitlist`/`counters`/`ratelimits`, and tightening before the writer exists costs nothing (the function writes through the Admin SDK and bypasses them regardless).
  - **⚠️ VERIFICATION IS IDEMPOTENT, AND THE SURVIVING TOKEN HASH IS THE MECHANISM — DO NOT TIDY IT AWAY (26 Aug).** On the **success** and **cap-full** paths `verifyWaitlist` keeps `verifyTokenHash` and records `verifyTokenSpentAt`; on the **expired** and **unsubscribe** paths it still nulls the hash. **That split is the whole safety argument**: the first two reached a terminal *"you are in"* state, so the hash is only a lookup key returning "you're in" to someone who already had the link; the second two did not, so a live hash there would be a replayable credential.
  - **THE REASON IS MAIL SECURITY SCANNERS, NOT TIDINESS.** Outlook Safe Links, corporate gateways and some antivirus tools **GET every URL in an inbound email before the recipient sees it**. With the hash nulled on first use the scanner's fetch IS the verification — it takes the founding place — and the writer's own click finds nothing and is told `unknown`. A routine failure mode of GET-based verification, not an edge case.
  - **⚠️ NULLING IT LOOKS CORRECT AND WAS THE ORIGINAL CODE.** That is why the reasoning sits in a comment at the value AND why `waitlist.emulator.spec.ts` asserts the **mechanism** (the hash survives, `verifyTokenSpentAt` is set) separately from the behaviour — a behaviour test alone would pass for the wrong reason if the record could be found some other way.
  - **⚠️ THE `already` BRANCH SITS ABOVE THE EXPIRY CHECK, DELIBERATELY.** Once you are in, you are in: a verified writer whose 48-hour window has since lapsed must not be told their link expired, because their place no longer depends on that window.
  - **HISTORY, because it is the better warning:** that branch was **unreachable from the day it was written** — every path setting `verified`/`waiting` also nulled the field the lookup queries on — while its own type comment said *"Clicking the link twice is not an error"*. The test that would have caught it **had never run**: its file failed to import in CI for as long as it existed. Two wrong halves, neither able to tell you.
- **⚠️ THE FIVE VERIFY OUTCOMES NEED A LANDING EXPERIENCE, AND TODAY THEY HAVE NONE (standing spec for the email pass).** The handler redirects to `/founders?verified=<kind>` and **nothing in `src/` reads that parameter**, so all five outcomes render the same page and a writer clicking their link is told nothing at all. Build it as five states with the discipline the founding panel already applies to the form — **not a parameter toggling a line of text**: **`verified`** *You're in* — position, what happens next, when to expect an invite · **`already`** already confirmed, warm and definite, **never reading as an error or a scolding** · **`waiting`** the cap filled while they were in their inbox — the unavoidable race, and the state that most needs real words · **`expired`** 48 hours passed, offer a resend · **`unknown`** a link matching nothing, neutral and not accusatory.
  - **⚠️ EXPECT `already` TO BE THE FIRST STATE A REAL WRITER SEES, FAR MORE OFTEN THAN INTUITION SUGGESTS** — because the scanner above verified them before they clicked. Copy that treats it as the unusual case is copy that will greet a large share of founding writers by implying they did something wrong.
- **⚠️ WHEN THE RETENTION JOB IS BUILT (email pass), NULLING SPENT TOKEN HASHES AFTER 90 DAYS IS PART OF ITS REMIT.** `waitlistStore.ts` carries a note at the value saying a job *may* do this and **explicitly fencing that none exists yet** — a comment describing a job that does not exist is the same fault as a comment outliving what it described, arriving from the other direction. **When the job lands, that comment stops being aspirational and must be rewritten to describe what actually runs.**
- **⚠️ THE PROD COUNTER STARTS AT ZERO AND IS NEVER SEEDED FROM DEV.** Dev's `counters/waitlist` holds test submissions made by whoever was verifying the mechanic; copying it to prod would state a number of founding writers that does not exist, on a public page, permanently. The function creates the counter lazily on first use — let it. **If prod's holding page has real historical sign-ups, that is a migration question about `waitlist/` documents, not a licence to carry a count across.**

It is never seeded, never rounded and never floored to look healthier.** A floor of 20 existed so `3/100` would not sit on the page saying nobody wants this; the better answer is to seed the list with GENUINE sign-ups, so the floor is `0` (`COUNTER_FLOOR`, `functions/src/waitlistModel.ts`). The mechanism stays — `visible`, the conditional omission of `count`, the client's live-or-absent render — so raising it again is one constant, not a redesign.
  - **⚠️ ZERO AS A FLOOR IS FINE; ZERO AS A FALLBACK IS NOT.** An unreadable count must render NOTHING. `readCounterState` returns **`null`** when the counter document is absent, and `countPayload(null)` omits `count` entirely — because a missing document is not evidence that nobody signed up, it is evidence that we do not know, and `0/100` on an outage is a false claim about how many founding writers there are, made by accident, on the one page whose whole design is that the number is the number. Inside the transactions a missing counter genuinely does mean zero (it is created lazily), which is why only that one reader distinguishes them.
  - **The live-or-absent rule is unchanged and is the ONLY reason the counter ever hides.**
- **⚠️ THE `full` STATE IS REACHABLE NOW, AND IT COMES FROM THE SERVER RATHER THAN FROM ARITHMETIC.** It was written and unreachable for a year, deliberately, while `functions/src/waitlist.ts` returned `cap` in every response and enforced it nowhere — so a 101st sign-up succeeded and was told it was in. The function now writes `status: "waiting"` past the cap and answers `full: true`; `classifyJoin` reads **that flag and nothing else**. **Deciding it client-side from `count >= cap` remains forbidden**: two browsers racing past 100 both read 99, and only the transaction knows which of them got the last place. Because the copy and the state were settled in advance, turning the cap on needed no copy decision and no change to the store's state machine — the whole client change was one union member and one `if`. **That is the argument for declaring an unreachable state when you know it is coming, rather than the argument against it.**
- **⚠️ THE CONTAINER-CAP PRE-CHECK IS A LOCK NOW, NOT A HABIT** (`marketingTokens.test.ts`): given `clamp(min, Nvw, max)`, `max / N` must be at or below the container's own `max-width`. It asserts the RELATION, not the values, so a legitimate redesign passes and a wrong one does not — verified red against the historical 3.85rem, which reaches its ceiling at 1369px against a 1300px cap. ⚠️ **AND IT DOES NOT APPLY WHERE THE MEASURE IS A SELF-SCALED `ch`.** `.mk-beta h2` and `.mk-sect h2` both carry `max-width: Nch` on the element that sets the font-size, so the measure grows in lockstep with the type and the line count cannot change; the fault needs a **capped container** setting the measure while a viewport-relative size keeps climbing. That is why the lock's table is explicit rather than a sweep over every clamp in the file. ⚠️ **STATED GENERALLY, BECAUSE THE ARITHMETIC ALONE MISLEADS: the rule bites when type grows against a measure that has STOPPED growing.** Where the measure is expressed in the type's own units — a `ch` on the element that sets the font-size — the two cannot diverge and the cap is irrelevant however far past it the ceiling sits. `/founders`'s lifted line reaches its ceiling at 1333px against an 1180px cap and is completely safe. **Put that note at the value, not only here**: someone will run the check, see 1333 > 1180, and reach for a ceiling reduction that shrinks the line for nothing.
- **⚠️ A MARK BESIDE A HEADLINE IS AN INLINE ELEMENT BOUND TO THE LAST WORD, NEVER A FLEX SIBLING — unless the headline can never wrap.** *(24 Aug, the hero's tick; the ref draws the flex row and is right for its own page.)* A block flex item takes the whole available width and wraps its text INSIDE that box, so the moment the headline wraps the mark is pinned to the column's far edge with a hole between it and the words (measured ~40px at 1100). A plain inline mark fixes that and introduces the mirror fault — it drops onto a line of its own wherever the words fit and the words-plus-mark do not, at exactly the same width. **Both are fixed by binding the last word and the mark in a `white-space: nowrap` span** so the line breaks in front of both. The copy constant stays whole and the component splits it for typesetting; a lock reads the RENDERED heading, strips the markup and requires the sentence back, because a split is one dropped space from a silent copy change no verbatim lock on the constant could see.
