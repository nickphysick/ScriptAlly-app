# ScriptAlly — Project Notes

## Working discipline (READ FIRST — repo hygiene rules, locked 8 Jul; supersedes the old "Multi-stream protocol" model)
- **Direct-to-`main` only.** No feature branches, no PRs, no auto-merge. Solo dev, no live users — work lands on `main` directly. (Historical branches/PRs were consolidated 8 Jul; if you find yourself creating a branch or opening a PR, stop — that's not the workflow.)
- **CI-on-push is fine and stays.** `.github/workflows/ci.yml` (typecheck + tests + build on every push to `main`) is the safety net — keep it. It is NOT the same thing as PR gating; direct-to-main pushes still get verified.
- **⚠️ A RENDER HARNESS LOADS `dist/assets/index-*.css`, NEVER A HAND-PICKED LIST OF SOURCES.** Inlining `index.css` + the component's stylesheets omits **Tailwind's preflight**, so every box in the harness is `content-box` while every box in the app is `border-box`. On 6 Aug that difference produced a *measured, locked and deployed* fix that was wrong in the opposite direction: padding-only measured as aligned (48.0) in the harness and left the pill at 41.0 against the bar's 48.0 in the app, while the correct shape measured as an overshoot. **Every number was real; they described a page the app never serves.** A rule whose maths depends on the box model should also **declare `box-sizing` itself** rather than inherit it. Related measurement traps in that pane: `getBoundingClientRect` returns **zeros** (its `documentElement.clientHeight` is 0, so `100vh` collapses) — use `offsetTop`/`offsetHeight`, pin explicit pixel dimensions instead of `100vh`, and take a screenshot first to force layout or the first JS call still reads zeros.
- **⚠️ A RED CI EMAIL IS NOT NECESSARILY A RED BUILD — check whether the job ever got a runner.** Twice on 6 Aug a run sat queued 15 minutes and died with *"The job was not acquired by Runner of type hosted"*: GitHub's queue timeout, reported as **run conclusion `failure` with job conclusion `cancelled`**, which is what sends the "Run failed / All jobs were cancelled" mail. Nothing in the repo had failed either time.
- **⚠️ AND BEFORE BLAMING THE REPO FOR ANY CI ODDITY, CHECK `githubstatus.com`.** That day's cause was a **critical GitHub Actions incident from 15:22 UTC** — *"workflow runs are failing or delayed, and some queued jobs may time out"*, plus webhook delays that meant a push to `main` produced **no run at all**. The correlation was exact: every run before 15:22 passed or failed for a real reason; every anomaly is after it. The first diagnosis — that bursts of commits starved the queue — was **wrong**, and the evidence for it (the starved run being the older of two in flight) was a coincidence of timing. One `curl` of the status API would have led with the answer instead of arriving at it third. **`workflow_dispatch` is on `ci.yml`** for the tail of exactly this: `gh workflow run CI --ref main` verifies the tip without an empty commit when a run went missing. **The tell is `runner_name`** — `gh api repos/<o>/<r>/actions/runs/<id>/jobs`: a job that ran and genuinely failed names the machine that ran it and has steps; a starved one has `""` and no steps at all. Two defences are now in the workflows and neither should be removed casually: **`ci.yml` carries a per-ref `concurrency` group with `cancel-in-progress`** (both starvations were the OLDER of two runs in flight during a commit burst — main is linear, so verifying the tip verifies everything under it, and a concurrency-cancelled run ends `cancelled`, so it does not notify), and **`ci-retry.yml`** re-runs a failed run ONCE, but only when *every* job **executed zero steps**. (That discriminator started as "no runner was ever assigned" and **missed the very next infrastructure failure** — *"The hosted runner lost communication with the server"*, which HAS a runner name and still runs nothing. Zero completed steps is the honest signal: a real code failure always leaves steps behind.) **Retrying on `failure` alone would re-run real red builds until they went green by luck** — the discriminator is the whole point, and it was verified against the two real starved runs and the one real test failure before it shipped.
- **One active session per working tree.** Never run two sessions in the same checkout. For genuinely parallel work, each session gets its OWN worktree: `git worktree add ../ScriptAlly-<task> main`. Clean up worktrees when done (`git worktree remove`); end state is normally just the primary tree `/Users/nickphysick/ScriptAlly-app`.
- **⚠️ STEP 0, BEFORE ANY RECON: confirm the worktree is LEVEL WITH `main`** (`git rev-list --count HEAD..main` = 0). This has bitten twice — most recently a shell rebuild whose recon ran against a base **40 commits stale**, which would have produced conflicts in every file it touched. It is a one-line check and it belongs ahead of reading any code, because everything recon concludes is wrong if the base is.
- **Before any task:** confirm `HEAD` is on `main` and the tree is clean. If it isn't, STOP and report — do not proceed on top of unexplained dirt. Never `git switch` / `git stash` / `git checkout --` / `git restore` / `git clean` a checkout another session may be holding.
  - **⚠️ AND HERE IS WHAT TO DO INSTEAD, BECAUSE THE PROHIBITION ALONE IS BROKEN UNDER PRESSURE.** The moment it gets broken is always the same: a red gate, and a plausible-looking way to isolate it — *"I'll just stash their files, confirm the red is theirs, and put it back."* That is the exact shape of a near-miss recorded on 26 Aug: the stash and pop both succeeded and nothing was lost, but a conflict, or the other session writing inside that window, would have destroyed uncommitted work belonging to somebody else. **The near-miss is the finding, not the outcome.**
  - **TO ESTABLISH PROVENANCE OF A RED, READ — DO NOT MOVE.** `git status --short -- src/` names whose files are dirty; the failing test's own imports name what it exercises. If it imports nothing you have touched, it is not yours, and you have proved it without moving a byte. Two commands, no risk, and it works while the other session is still typing.
- **Stage by explicit path** (`git add <path>` then `git commit --only -- <paths>`); never `git add .` / `git add -A`. `git diff --cached --name-only` should list only the paths you intend. Gates green (tsc + production build + full Vitest, with `set -o pipefail`) before every commit.
- **⚠️ THE BUILD'S OUTPUT IS READ IN FULL, OR GREPPED — NEVER BY `tail` ALONE, AND A GREEN EXIT CODE IS NOT A CLEAN BUILD.** `vite build` prints CSS diagnostics near the TOP and exits 0 anyway, because they are warnings. Measured 18 Aug: a `css-syntax-error` from a malformed comment sat at **line 7 of 185** while every gate reading in this repo takes the last few lines — so it was printed on every single build for as long as the damage existed, and no gate could ever have failed on it. The browser was discarding a whole rule the entire time. Use `npx vite build 2>&1 | grep -inE "error|\[WARNING\]"` (the chunk-size note is the one expected match) or read the whole log; `tail -4` is how this hid.
- **⚠️ ON THE QUERY CENTRE TIMELINE, A DASHED BORDER MEANS PROVISIONAL AND NOTHING ELSE** — the scheduled-nudge ghost (`.tl-ghostmark`/`.tl-ghostpanel`) and the writer's own expected date (`.tl-wbar--est`/`.tl-waitmark--est`), both "not established fact". `.tc-chip.tc-reopen` wore it as an ACTION affordance and was retired to the base chip look (20 Aug): a third meaning three inches from the other two dilutes a grammar two features now read. **The pane is a different surface and keeps its own uses** — `.qp-inplace`'s dashed underline (editable in place) and `.f12-addmat`'s dashed add tile are both fine and deliberately untouched.
- **⚠️ A LOCK READING CSS AS SOURCE PROVES A RULE WAS WRITTEN, NEVER THAT IT REACHED AN ELEMENT.** The pair retired on 18 Aug required `flex: 0 0 auto` on `.tpl-head` by searching the stylesheet text — and passed for months over a declaration the browser was discarding, about a class no component renders. **Doubly vacuous: a property that never applied, to an element that never existed.** 21 such assertions across 13 suites remain and are fine as they stand — a source lock is the right tool for *"this token is still emitted"* or *"this selector is not restated"*. It is the wrong tool for *"this element ends up laid out like so"*: that claim is measured on a rendered page (`npm run e2e`), never read out of a file. Forbidding a class in a sheet is a different and legitimate claim from requiring a property on it.
- **⚠️ AFTER STAGING, `git status` MUST SHOW A CLEAN TREE BEFORE THE GATES ARE BELIEVED.** Explicit-path staging is the right rule and this is its cost: it will silently omit a file you changed *for the very reason you are committing*. If anything is still modified, the suite you just ran was run against a tree the commit does not contain — so "green locally" proves nothing about what you pushed. This is not hypothetical: on 6 Aug a retargeted lock in `src/lib/` was left behind by a commit that staged `src/components/todo/`, the local suite was green, and CI — which only ever sees what was pushed — was right where I was not.
- **⚠️ INITIALISATION CALLS GO AT THE END OF A MODULE, never at the foot of a block that a later block extends.** A `var`-hoisted table read by an earlier init call is `undefined` at that moment, and the throw silently kills every later initialiser — so the failure surfaces as unrelated features going quiet rather than as an error anyone can trace back. The same shape catches `const` in a module's temporal dead zone, and **`tsc` only sees it when the reference shares the declaration's scope**: read the same `const` from a helper the render calls and it typechecks clean (see the TDZ note above). Comments are not guards here either — **assert the initial render state in a test**, because a module that throws on load renders nothing and a source-string suite will not notice.
- **⚠️ COMMENTS ARE NOT GUARDS. A constraint worth a warning comment is worth a test.** A `⚠️` in a file is a note to whoever happens to read that line; it stops nothing. Also on 6 Aug, `ToDoPage.tsx` carried a verbatim warning against declaring a post-return `const` that the render reads — and the bug was written into that same file, in a session that had read the comment, and shipped to dev as a page that would not load through a fully green suite. If you find yourself writing "⚠️ never do X here", write the assertion that fails when someone does; the comment then explains the test rather than standing in for it.
- **⚠️ A NEW ROUTED PAGE SHIPS WITH A SMOKE TEST FROM DAY ONE.** One entry in `src/test/pageSmoke.tsx`'s census, one file asserting the page renders + one distinctive chrome string — the pattern in `dashboardPageSmoke.test.tsx` and its siblings. **This repo's tests read SOURCE** (`vitest.config.ts` is `environment: 'node'`; no jsdom, no testing-library), and a source-string test cannot see a runtime crash: it proves the code was written, not that it ran. Keep the assertions minimal — a smoke that pins appearance becomes the next false red. **Smoke the POPULATED state too wherever the page branches to a first-run panel**, or every derivation on it stays unexecuted. Full inventory + rationale: `reports/app-smoke.md`.
- **⚠️ `tsc` DOES NOT CATCH THE TDZ BUG — do not assume a green typecheck covers it.** Used-before-declaration (TS2448) fires only when the reference shares a scope with the declaration. The shape that actually shipped read the `const` from inside a **hoisted helper the render calls**, which TypeScript treats as legal because it cannot know the helper runs during render. A direct `description={helper()}` in the JSX *is* caught by tsc — so **testing a guard against that shape proves nothing**. Verified 6 Aug: the real shape reintroduced into `AllManuscripts.tsx` passed tsc AND the production build, and was caught only by the render smoke and `pageStructure.test.ts`.
  - **⚠️ THE THIRD SHAPE IS AN IIFE, AND BEING CAUGHT BY TS2448 IS WHAT MAKES YOU MISS IT (26 Aug).** A `const` whose initialiser is an immediately-invoked arrow runs **at its declaration**, so a read of any `const` below it is a TDZ — and `tsc` cannot see through the IIFE any more than through a hoisted helper. The journey round hit BOTH halves in one session: `closeReason` reading `activeFlow` from the same scope was correctly refused with TS2448, one declaration was moved, and the shape was treated as closed. It was not — `paneWill`'s IIFE read the same two `const`s from two hundred lines above them, compiled clean, passed **6,995 unit tests** and a clean production build, and threw `Cannot access 'Rr' before initialization` inside `useTaskPaneSession` on every render with a docked card. **The whole To-do page fell into its error boundary the moment a task was opened, and it reached `main` that way.** So: **TS2448 is a signal to audit every render-time read in that function, never a sign the problem is handled** — and the rule to apply is the ORDER (anything a render-time expression reads is declared above it), which is lockable as `indexOf(dep) < indexOf(consumer)` with BOTH halves asserted, since an ordering lock over a consumer that stopped reading its dependencies passes forever.
- **PROD deploys are Nick's only — never Claude.** Claude Code never runs `firebase deploy` against **prod** (hosting, functions, or rules — i.e. `firebase.json` / `firebase.holding.json`). **DEV deploys are fine whenever Nick asks:** `npm run build:dev && firebase deploy --only hosting --config firebase.dev.json --project dev` (hosting-only unless functions/rules changed). (Clarified 14 Jul — supersedes the earlier blanket "no deploys" line, which contradicted the long-standing dev-on-request workflow.) **⚠️ AMENDED 18 Aug: dev FIRESTORE RULES no longer need asking — see the Deployment section, which owns the command and its before/after checks.**

## App shell — the desk, the capsules and the alignment contract (app-shell pack, 5 Aug; refs = design-refs/scriptally-sage-desk.html + scriptally-topnav-v2.html)
- **⚠️ THE ALIGNMENT CONTRACT IS A RULE, NOT A SET OF VALUES.** Four tokens expansion never touches — `--gutter` (20px, the icon box's x), `--icon` (38), `--pitch` (42, parent row), `--kid` (34, child row) — plus `--head` (72, driving BOTH capsules' headers) and `--col-min`/`--col-max` (78 ↔ 246). On expand **only labels, chevrons and children change; icons do not move.** Alignment is **structural, not maintained**: the icon sits at `--gutter` in both states because both read the same token, not because two numbers were matched by hand. **If a future change moves an icon between states, the token is being bypassed — that is the bug**, and the fix is to put the row back on the token, never to nudge the other state to match.
- **⚠️ `align-items: baseline` ON AN IMAGE ALIGNS ITS BOTTOM MARGIN EDGE — images have no baseline.** *(Measured 9 Aug: the pagebar wordmark sat **7.6px low** beside the crumb, and every value in the rule was the one intended.)* A row mixing **text and images** cannot be baselined: the text aligns on its baseline, the images on their bottoms, and the taller image drags. Two consequences that both bit in the same pass: the brand row uses **`align-items: center`** and pays for the optical difference with an explicit padding contract (19px top / 16px bottom) rather than by nudging one child; and **a text element that lands inside a baselined container inherits the trap** — the save state was 3.7px low as a `.ws-crumb` child and correct as a pagebar child, with no CSS of its own changed. **If a child is mysteriously low, check what its container aligns on before you touch the child.**
- **⚠️ THE DESK AND THE ACTIVE FILL ARE TWO TOKENS, and they used to be one.** `--shell-ground` was both the ground and the nav's active-row fill under the old law *"active = a window cut through to the page ground"*. **That law only held while the ground was neutral cream.** Cut a window through to sage and the metaphor produces a **green pill**. So: **`--shell-desk: #aebdb0`** is the ground and *nothing else reads it*; **`--shell-active-fill: #ffffff`** is the selector and every `.on` state. **THE LAW, RESTATED: active is a BRIGHT SURFACE LAID ON the capsule, not a hole cut through it.** The old sentence is deleted rather than left standing — it would re-generate the bug the next time someone touched it.
- **⚠️ It is `--shell-desk`, NOT `--desk`.** `--desk` was already taken: the per-theme working-area background (Capp `#e8ddd0` · Bold `#c2cfda` · Editorial `#f4f4f3`) that the hubs and the ultrawide margin rule read. A `:root --desk` would have been overridden by every theme class **silently** — the desk would just have come out the wrong colour with nothing to point at.
- **⚠️ THE SHELL RENDERS WHAT EXISTS, NEVER WHAT IS PLANNED.** *(Nick's own note: the pack's lists were written from the product he wants, not the routes we have.)* **Any nav list in a pack is a PROPOSAL to be checked against the router, not a specification.** Roughly half the top-nav's mega-menu items had no route — Progress, Archive, Agencies, wish lists, response times, Query letters, Synopses, Opening samples, Downloads — and every one is **absent**, not dead and not greyed: a nav item that goes nowhere teaches the wrong shape of the app, and a greyed one hints at a roadmap in the chrome. The rail follows the same rule, and **the two surfaces must not diverge** (locked: `topNav.test.tsx` asserts the rail's model has none of them either).
- **⚠️ THE TOP NAV HAS THREE HEADINGS — Queries · Agents · Materials.** `Learn` was dropped: its only real destination is Help centre, which the shared account menu already carries, so nothing became unreachable. **A heading that opens onto one link advertises a section that does not exist.** It returns when there are guides to put in it.
- **⚠️ MEGA-MENU COLUMNS COME FROM CONTENT, never three reserved slots** — three fixed columns holding two items looks broken, and the menus are thinner than the mockup drew them. One component, `--cols` set from the data. The right-hand **live-data panel stays in every menu** and now carries more weight than the mockup asked of it: it is what stops a short menu looking empty.
- **⚠️ AN INSET FILL NEEDS A SURFACE IT CAN ACTUALLY SIT ON.** `--shell-inset` (`#efe8df`) is **near-invisible on the column** (`#efe7db` — measured within 0.01 relative luminance) and **a real step on the content capsule** (`#f7f2e9`). So it is retired from the column and kept everywhere else. On the column, a control that needs to read as a surface takes **white fill + 1px `--shell-line` hairline** — which is what the ghost `Record a response` button already does. **Do not delete the token app-wide:** on menu and palette rows it is the hover, and replacing it there would put a bordered box under the pointer instead of a wash. *(Nothing needed deleting in the end — the column's only fills are the selector and that ghost button, so it already obeyed the rule; a lock now keeps it that way.)*
- **⚠️ HEADER HEIGHT ON A FIXED-HEIGHT MASTER–DETAIL SURFACE IS TAKEN DIRECTLY FROM THE PANES BELOW.** That is why `PageHeader`'s `compact` flag exists, and why it wins over the tool row: the row is the default layout, but **on a compact page the actions stay INLINE on the title row**, because giving them their own row adds back exactly the height compact was built to remove. One layout, one density flag — and the flag already governed alignment, so governing row-versus-inline is an extension rather than a new concept.
- **⚠️ THE SELECTOR NEVER MARKS A ROW THAT IS NOT RENDERED — a collapsed child resolves to its parent.** The floating selector is the column's ONLY active marker, so what it points at is the whole answer to "where am I". Children are hidden while the column is collapsed, so honouring a child target there would leave the one marker floating over a row that is not on screen. **A decision, not a missing case — do not "fix" it.** (`selectorBox`, locked as state four of four.)
- **⚠️ THE SHADOW TINT BELONGS TO THE DESK'S COLOUR FAMILY AND MOVES WITH IT.** Four stops, green-grey `rgba(56,66,58,…)` because the desk is sage. **A cool-blue or warm-brown shadow on a sage desk reads as dirt rather than depth.** The stops are just the shape; the tint is the rule. Capsules also carry a **white top rim** (`--shell-cap-rim`) — without it they read as holes cut in the desk rather than objects resting on it.
- **⚠️ THE MOCKUP-WINS RULE HAS ONE CARVE-OUT.** A mockup wins on **what it shows**, but **not where the pack names a value and gives its reason** — a reasoned value in prose beats an unreasoned one in an artefact. (Case in point: `scriptally-sage-desk.html` still ships a blue-grey `--lift` left over from the pastille sheet's blue desk. That line is **fenced as stale in the committed ref**; the shipped tint is green-grey.) Fence stale lines in place rather than editing the ref, per the house treatment of partially-current refs.
- **⚠️ CHECK FROM CONSUMPTION TO DEFINITION, NOT DEFINITION TO CONSUMPTION.** *(The finding of this project.)* `calc()` on an **undefined** custom property yields `NaN`, and CSS says nothing: the declaration is simply dropped. `--pad-r` was read by four rules — including the shell selector's width — while being defined nowhere, so **the only active marker in the shell rendered 0px wide** with **tsc, 2,259 tests and a production build all green**.
  - **Why the obvious guard missed it:** the earlier rule was *grep `dist/` for the tokens you added*. **Checking that what you wrote arrived cannot catch what you referenced and never wrote.** The direction was wrong, not the idea.
  - **The rule:** every `var(--x)` a stylesheet READS must resolve to a definition — asserted in `shellV2Tokens.test.ts` ("no shell rule reads a token that does not exist"). Pointed this way it immediately found two more: `--sv2-flank`, left dangling when Phase 3 deleted `.sv2-tb-dash`, and `--shell-ease`, which named nothing behind an inline fallback.
  - Still also grep `dist/` after adding or renaming a token — a green build proves the CSS parsed, not that it contains what you wrote (see the swallowed-comment note below). The two guards catch opposite mistakes.
- **⚠️ A PSEUDO-ELEMENT KEEPS ITS OWN TRANSITION.** Suppressing the transition on `.x` does NOT reach `.x::after` — target it directly (`.x::after { transition: none !important }`). The top-nav hairline measured opacity `0` in BOTH states and looked like a dead rule; it is 0 → 1.
- **⚠️ SUPPRESS TRANSITIONS BEFORE MEASURING — a transitioned property reports where it STARTED, not where it is.** This has now cost time twice, and both times it looked like a real bug: a **collapsed column measured 246px** (its expanded width) and **the fade's opacity measured 0** while its class was on. Set `el.style.transition = "none"` before reading, or read after the transition has demonstrably finished. In the in-app browser pane specifically, transitions do not reliably advance at all, so `getComputedStyle` returns the start value indefinitely.
- **⚠️ A CUSTOM PROPERTY COMPUTED AT `:root` CANNOT BE OVERRIDDEN BY A LOWER VARIANT; ONE READ INSIDE A `calc()` RESOLVES AT THE USE SITE.** *(Query Centre, 13 Aug — and the two look identical from a distance, which is the whole cost.)* `:root` sets `--content-top-gap: var(--content-top-gap-rest)`, so the value is **already resolved** by the time any page sees it: overriding `--content-top-gap-rest` further down changes **nothing**, and the page-scoped rhythm had to name `--content-top-gap` itself in both states at 0-2-0. `--header-inset` is read inside `calc(var(--content-gutter) + var(--header-inset))` on `.wpg-plate`, so a **use-site** resolution — overriding it on an ancestor works, and one page-scoped line took the masthead from a 120px-inset island to a full-width band without touching the shell's law or the other nine pages. **The test is not "is it a token" but "where is it evaluated": a variant read into a resolved property at `:root` is spent; a property read inside a `calc()` is live all the way down.**
- **⚠️ A MALFORMED CSS COMMENT SWALLOWS TOKENS SILENTLY.** A declaration left outside its `/* */` produced **no token and no error** — the build succeeded, the tests passed, and the desk was simply the wrong colour. Every shell token now sits in `shellV2Tokens.test.ts`'s `BAKED` map for exactly this reason: a value asserted there fails the moment it stops being emitted.

## Navigation & shell architecture (post-AppShell rollout `88db5f7`+`4933aca`, live on prod)
- **⚠️ THE BREADCRUMB IS CHROME — A PAGE MUST NEVER RENDER ITS OWN (app shell v2, 9 Aug).** It is
  drawn once by `WorkspaceShell`, on the page ground ABOVE the content window, from the pure
  `shellCrumb`. It therefore does NOT scroll with the content. A page drawing its own would give
  two crumbs that disagree the moment a route's naming changes. If a page needs different words,
  the fix is `shellCrumb`'s table — never a local render.
- **Global shell = `src/components/shell/AppShell.tsx`**, rendered once: persistent left rail (240px ↔ 60px via the edge chevron; state in `localStorage["scriptally.queriesRailCollapsed"]`), never remounts on navigation. The desktop top bar is RETIRED — `Nav.tsx` survives only as the below-`md` mobile slim bar (alongside `BottomTabBar`). **The rail's anatomy was REBUILT 5 Jul (grouped index + capture + utility — see the Rail rebuild section below); the old flat-four-items + bell/settings icon-row description is superseded.**
- **Routing = `react-router-dom` (BrowserRouter).** New code uses the router directly; `handleNavigate(tab, sub?)` in `App.tsx` is a bridge (`pathFor`) for legacy call sites. The three focus-form interceptions ("Log a query"/"Send a query", "Add an agent", "Add a manuscript"/"Add a Manuscript") open overlays and NEVER navigate; `searchQuery` clears on real navigation only.
- **Route map (now TIERED — see the Route tiers section):** workspace `/dashboard` · `/queries` (`?q=<id>` deep-selection, `?view=landing` legacy) · `/agents` · `/agents/discover` · `/manuscripts` · `/manuscripts/packages` · `/import` (+ guarded `/email-import-dev`); marketing `/` (Landing) · `/pricing` (Pricing); focus `/account` · `/plans` (PlansPage — a DISTINCT page from Pricing; consolidation is an open decision, never merge silently) · `/help`. Unknown paths → `/dashboard`. Pre-auth `#/login`/`#/signin`/`#/signup` and the DEV-only lab hashes coexist with the router (hash ≠ pathname); hosting rewrites (`** → /index.html`) cover deep links.
- **Main pages stay MOUNTED** — dashboard/queries/agents/manuscripts are persistent `StagePage` slots (display toggling). Page-local state (Queries filters/sort/selection) must survive navigation — never "fix" by unmounting. StagePage's enter-animation class self-clears (animationend + 250ms timeout): while it runs, its transform makes the slot the containing block for `position:fixed` page furniture — do not simplify that away.
- **The stage (`#app-stage-scroll`) is the scroll container**, not the window. Page heights are stage-relative — no `calc(100vh - 64px)`-style bar offsets, ever. Overlay scroll locks go through `src/lib/stageScroll.ts` (stage + body, wedge-proof release), never `document.body`/`window.scrollY` alone. Per-route scroll position is remembered on the stage element.
- **Themes:** the `.t-capp`/`.t-bold`/… class lives on the AppShell ROOT; tokens in `index.css` (incl. `--navpill`); persisted in the user doc `queriesTheme`; two controls (rail-foot seg + Settings radio) write the same field. Form 11 inset frame is Cappuccino-only (`.t-capp .qhbar::after`). The rail chrome is themed on every page; non-Queries page interiors keep hard-coded styling until the parked page-unification phase.
- **Shell CSS footgun:** the rail's and help-FAB's `display` comes from classes + media queries, NOT inline (inline display beats Tailwind breakpoint utilities); the rail collapse rules need `!important` against inline-critical styles.
- **Dead-but-present, awaiting a cleanup commit:** `Nav.tsx` desktop paths, legacy `src/components/AppShell.tsx`, `SidebarShell`/`ShellChrome` (still power dev `#/shell-lab`).

The probe signs in as the harness user and attempts one field at a time, each labelled with the commit it arrived in, undoing every write — so the answer is *which commit the deployed ruleset stops at*. It found the real cause twice in one day: once a deploy that simply predated the commit it was expected to carry, and once a denial that had nothing to do with rules at all (see below).

- **TWO TIERS, TWO MECHANISMS, BOTH EXPLICIT.** The client reads **`VITE_FIREBASE_DATABASE_ID`** (`src/lib/firebase.ts`, from `.env.production` / `.env.development`). Functions read **`FIRESTORE_DATABASE_ID`** (`functions/.env.<projectId>`, loaded by firebase-tools at deploy). Neither infers the other; there is no shared file and no JS mirror to keep in step.
  - **⚠️ IT CANNOT BE CALLED `FIREBASE_DATABASE_ID`.** firebase-tools reserves the prefixes `X_GOOGLE_`, `FIREBASE_` and `EXT_` and its own `validateKey` refuses one outright (`lib/functions/env.js`). The rejection lands at deploy time, not in the editor.
- **⚠️ NO FUNCTION MAY CALL `admin.firestore()` OR `getFirestore(` — LOCKED, not merely agreed.** `functions/src/firestore.ts` owns the single handle and the single `initializeApp()`; everything else does `import { db } from "./firestore"`. `firestoreHandle.test.ts` scans every file and fails on a second one. **The exempt set is exactly `["waitlist.emulator.spec.ts"]` and its SIZE is asserted** — a harness that must pin a demo projectId and reach the emulator. Without the size assertion the rule erodes one exemption at a time.
- **THE GUARD IS STATED OVER THE RESULT, NOT THE INPUT:** on a project with no `(default)`, the resolved id may not **be** `(default)`. One clause closes two ways in — the variable unset, and the variable set to `(default)` on purpose. **The second is not hypothetical:** `.env.development` legitimately reads `(default)`, and copying that line into prod's slot reproduces the original bug exactly, with the variable dutifully set. On prod the functions then **refuse to start**, which is infinitely better than answering and writing nowhere.
- **⚠️ PROD IS NOT CONFIGURED AND THE FILE IS DELIBERATELY ABSENT.** `functions/.env.gen-lang-client-0801391782` with `FIRESTORE_DATABASE_ID=ai-studio-ae82196c-c59e-40b9-b209-9fb02f67ade6` is **Nick's to create, alongside the deploy it enables** — template in `functions/.env.example`. **It must exist BEFORE the next prod functions deploy**, and the two broken functions need redeploying once it does. Until then prod's functions fail closed rather than silently.
- **⚠️ `functions/.env.scriptally-dev` STATES `(default)` EXPLICITLY, WHICH IS NOT THE SAME AS OMITTING IT.** Dev would work either way — that is the point. **Explicit-and-correct and absent-and-lucky must be distinguishable**, because only one of them survives being copied to prod.
- **⚠️ `functions/` IS COMMONJS, SO `import.meta` COMPILES IN THE TEST RUNNER AND FAILS AT PREDEPLOY.** `functions/tsconfig.json` is `module: "commonjs"` and its `include: ["src"]` sweeps test files in, so `import.meta.url` — the ordinary way to locate a file — dies with **TS1343** under `tsc -p functions`, which is the **predeploy** step in `firebase.json`. **Vitest transpiles it as ESM and is perfectly happy**, so the break is invisible in every local loop and surfaces at a deploy, to Nick, mid-deploy. Locate a directory by search or by a path relative to `process.cwd()` instead — and make it fail loudly, naming what it looked for, rather than quietly scanning an empty directory.
- **⚠️ A SOURCE-SCANNING LOCK ALWAYS MATCHES ITS OWN SEARCH TERMS — SKIP THE SCANNER BY NAME, NEVER WEAKEN THE PATTERN.** `firestoreHandle.test.ts` has to spell `admin.firestore()` and `getFirestore(` out in order to hunt for them, and those sit in **regex literals — code, not comments** — so the house `stripComments` rule cannot reach them. It flagged itself on its first run, which is the cheapest possible evidence that the detection works. **The temptation is to loosen the pattern until the self-match stops; that silently loosens it for every real offender too.** Skip the one file, and keep that skip SEPARATE from the exemption list so an assertion like "the exempt set is exactly one file" still means what it says.
- **⚠️ THE ROOT TYPECHECK DOES NOT COVER `functions/`** — `tsconfig.json` excludes it, so `npm run lint` and CI's Typecheck step both skip it. It is typechecked by the **predeploy** step (`npm --prefix functions run build`) and nowhere else in the normal loop. **Run `npx tsc --noEmit -p functions/tsconfig.json` after touching anything under `functions/`**; this pass caught a TS1343 that way (`import.meta` is illegal under its `module: "commonjs"`, while vitest transpiles it as ESM and never complains) which would otherwise have surfaced at a deploy and nowhere earlier.

## Conventions & invariants
- **⚠️ THE OUTER GAP LOOKS WRONG ON ONE SIDE — and the geometry is fine.** *(Symptom first, because the symptom points away from the cause.)*
  - **Symptom:** the right-hand margin looks smaller than the left.
  - **Cause:** it is not. Both are `--shell-cap-gap`. The left band is *padding + rail + gap*, so it is physically wider; and the pale rail reads as margin against the pale ground, which widens it again to the eye. **Re-measure with `getBoundingClientRect` before treating it as a bug** — measured 30 Jul, both gutters 14px.
  - **Fix:** none needed. **NEVER add right-side padding to compensate.**
  - **The one real way it can break:** a `position: fixed` floater measures from the BROWSER edge rather than the content capsule (the timeline pull tab sat at `right: 0`; the help FAB carried an inline `right`). That is a genuine bug with a genuine fix — give the escapee `var(--shell-cap-gap)` — but it is a *different* fault from the perceived asymmetry above, and it is not fixed by padding either.
  - The token is one value for every edge **and** the inter-capsule gaps: **`--shell-cap-gap: 14px`** (it spent a spell at 10px and was returned). *(The packs call it `--shell-gap`; the token in this repo has always been `--shell-cap-gap` — same thing, one owner: `.sv2-app { padding: var(--shell-cap-gap); gap: var(--shell-cap-gap) }`.)*

- **⚠️ A `var()` ON A TOKEN NOBODY DEFINES IS A RULE THAT LOOKS PARAMETERISED AND IS NOT — AND IT SURVIVES EVERY SWEEP FOR THE TOKEN.** *(20 Aug, retiring the masthead's `--wsh-ctl-*` / `--wsh-pill-*` ladders.)* The tokens were deleted, and two page sheets were still READING them — `font-size: var(--wsh-pill-fs, 8.5px)`, `height: var(--wsh-ctl-h, 38px)`. Nothing broke, because a `var()` whose custom property has no definition falls back to its second argument. **That is exactly what makes it insidious: the page renders correctly, so no measurement catches it, and a grep for the token's DEFINITION finds nothing — which reads as 'already cleaned' rather than as 'still read'.** Meanwhile the next person to open that sheet sees a knob and goes looking for it.
  - **⚠️ THE SWEEP MUST BE FOR READS, NOT DEFINITIONS.** `grep -rn -- "var(--the-token" src` is the one that answers the question; `grep -- "--the-token:"` answers a different one and looks like the same answer. `shellV2Tokens.test.ts` already asserts the inverse for shell sheets — every `var(--x)` a stylesheet READS must resolve — and that lock is the reason this class is catchable at all.
  - **A FALLBACK IS FOR A TOKEN THAT MIGHT LEGITIMATELY BE ABSENT** (a page opting into a component's default). Once the token is retired, the fallback IS the value: state it, and delete the indirection.
  - **⚠️ AND THE OPPOSITE MISTAKE IS THE SAME SIZE: "THE TOKEN EXISTS" DOES NOT MEAN "THE TOKEN RESOLVES HERE".** *(25 Aug, sweeping this pack's fallbacks — the correction to the rule above, found by trying to apply it mechanically.)* A defined token still yields its fallback anywhere its **defining scope** is not an ancestor, so the identical construct can be dead weight in one file and the painted value in another. **Worked example, one token, two dispositions:** `--f12-serif` is defined once, on **`.t-f12`** — a theme class `Queries.tsx` applies and the packages page does not sit under. In `packageGroup.css` the token resolves and `var(--f12-serif, 'Playfair Display', serif)` is genuinely dead weight; in `packageTracking.css` it never resolves, so `Georgia, serif` is **what renders**, and deleting it as dead weight would silently have changed the font on a live surface.
    - **THE TEST IS THE SAME ONE THIS FILE ALREADY STATES FOR `--content-top-gap`: not "is it a token" but WHERE IS IT EVALUATED.** Before dropping a fallback, find the token's defining selector and confirm it is an ancestor of the rule's subject. `:root` always is; a theme class (`.t-f12`, `.t-capp`, …) is only sometimes.
    - **⚠️ A SOURCE LOCK CAN BE ASSERTING THE FALLBACK RATHER THAN THE VALUE.** `sentStrip.test.ts` read `toContain("Playfair Display")` and passed on the fallback string; the moment the fallback went, a lock about a family name failed over a font that had not moved. Assert the token where the value comes from a token.
    - **AND WHERE THE SCOPE ARGUMENT HOLDS, IT BEATS A SCREENSHOT.** A fallback applies only when the token is unset, so "the defining scope is an ancestor" proves the painted value cannot move — at every viewport and every theme, which one measured render does not.
- **⚠️ `height: 100vh` ON AN ELEMENT THAT DOES NOT START AT `y: 0` OVER-CLAIMS BY EXACTLY ITS OFFSET.** *(22 Aug, the Tasks chassis's unreachable 21px.)* `100vh` is the VIEWPORT's height, never "the height remaining from here down". `.ws-main` sat below the beta strip at `y: 41.75` and still asked for a full `100vh`, so its bottom landed at 941.75 in a 900px viewport; less its own 20px of padding, the last **21px of every Tasks page was below the fold with the document not scrolling**. It cost the Calendar a control — the day panel pins "Open the list" to its foot.
  - **⚠️ A CONSTANT OFFSET ACROSS VIEWPORT HEIGHTS POINTS AT A FIXED-HEIGHT ANCESTOR, NOT AT PADDING.** The same 21px at 800, 900 and 1000, on three pages, cannot be proportional or content-driven — it is a fixed contribution counted once too many. That shape is the fastest route to the culprit: walk the ancestry and find the first box whose bottom exceeds the viewport, rather than hunting for a stray `padding`.
  - **⚠️ AND `.sa-shellframe` CARRIES THE IDENTICAL DECLARATION AND IS CORRECT, because it sits at `y: 0`.** One element up the line is right, one element down it is wrong, and **nothing in the declaration distinguishes them** — which is how it survived review. Before writing `100vh`, ask what is above the element, and whether anything ever could be.
  - **THE FIX WAS A DELETION.** `.ws-app` is a flex row and `.ws-main` is `flex: 1` inside it, so default `align-items: stretch` already sized it correctly; the `100vh` overrode a right answer. **Never compensate with an offset** — a matching 21px anywhere is the "add padding to fix a gutter" mistake this file already records.
  - **⚠️ REMOVING AN OVER-CLAIM LOOKS LIKE A REGRESSION DOWNSTREAM, AND IS NOT.** The Calendar had been drawing into 42px that did not exist; with the claim gone its rows are honestly 7px shorter and its cells began to overflow. **The overflow was always there — it was being drawn off-screen.** Expect a correction like this to surface work elsewhere, and budget for it rather than reverting.
- **⚠️ THE QUERY LIST IS MANUSCRIPT-SCOPED, SO A DEFAULT-SCOPE CENSUS SILENTLY OMITS EVERY QUERY ON ANOTHER MANUSCRIPT — WHICH IS EXACTLY WHERE A STALE RENDER SURVIVES.** *(24 Aug, the Part D census.)* A sweep that clicks through the rows it can see reports a clean result about the subset it happened to be shown, and the omission is invisible because nothing states how many rows were skipped. **Sweep at scope All and REPORT THE COUNT SWEPT** — `44 of 44` is a census, `30 rows` is a sample wearing a census's clothes.
  - **⚠️ AND CHECK THE CONTROL EXISTS BEFORE BELIEVING YOU WIDENED ANYTHING.** Two of my own censuses said "scope All" and clicked nothing: `getByRole("button", { name: /^all$/i })` matched no control in that toolbar, and the guarded `if (await all.count())` made the miss silent. Those sweeps happened to be complete for a different reason — the list is not scoped by the shell's manuscript chip — so the counts stood and the stated reason for them was wrong. **A no-op widening step reads exactly like a successful one.**
  - **THE STRONGER FORM: compare the rendered row count against the STORED count.** `47 stored · 47 rendered · difference 0` cannot be satisfied by a filter you forgot to clear, and it is what caught `if (!agent || !ms) return false` dropping unresolvable rows at every scope.
- **⚠️ `force: true` ON A CLICK IS NEVER THE FIX FOR A TIMEOUT.** It skips Playwright's actionability check and dispatches at the coordinates the locator resolved to — which a hover-lift, a settle animation or a sticky reflow has already moved. **It opened a neighbouring control and reported correct code as broken:** a packages card's lift put `DUPLICATE` under the pointer and the click landed on `EDIT` (`title="EDIT PACKAGE"`), which read as the duplicate flow being wired to the wrong handler. **When a click times out, the element is telling you something** — it is covered, it is off-screen, it is a hidden mounted page's copy, or it has not settled. Fix that. Where a real overlay must be bypassed for a measurement, `el.evaluate((e) => e.click())` dispatches on the element itself and cannot land somewhere else.
- **⚠️ DISMISSIBLE CHROME HIDES LAYOUT FAULTS — when a bug reproduces in the harness but not by hand, suspect dismissed or persisted chrome before doubting the harness.** *(Same run.)* `BetaStrip` returns `null` once dismissed (`sessionStorage`), so the strip disappears, `.ws-main` starts at `y: 0`, and its `100vh` becomes momentarily correct. **Anyone who had clicked the × once saw a whole page and could never reproduce the fault; the harness gets a fresh session every run and therefore always saw it.** The offset was never a property of the chassis either — it was `(whatever sits above the shell) − 20`, so a banner of a different height would have changed it silently.

- **⚠️ A PAGE'S CLASS AND A COMPONENT'S CLASS ON THE *SAME ELEMENT* ARE DECIDED BY SOURCE ORDER — SO A COMPONENT DEFAULT SILENTLY BEATS EVERY PAGE OVERRIDE.** *(21 Aug, the masthead's gutter.)* A page names itself with a className passed straight to the component (`<WorkspacePageGrid className="qc-wpg">`), so `.wpg` and `.qc-wpg` both land on ONE element at 0-1-0 and the later stylesheet wins. `--wpg-gutter: var(--content-gutter)` on `.wpg` therefore overrode `.qc-wpg`'s tight value on every page — **measured: Query Centre's content sat at 342 with the wide gutter while To-do's sat at 297 with the tight one, from declarations that read correctly in both files.** The old override worked only because it was `.qc-wpg .wpg-scroll` — a *descendant* selector at 0-2-0 — and flattening it to the token lost the specificity nobody knew was load-bearing.
  - **THE FIX IS A USE-SITE FALLBACK, NOT MORE SPECIFICITY.** `var(--wpg-gutter, var(--content-gutter))` at the point of use has no contest at all: the fallback applies only when nothing declared the token anywhere, which is exactly what "the page did not ask for a gutter" means. Raising specificity instead wins today and loses the day someone adds a third class.
  - **THE TELL** is a token declared on a component root that any page is also expected to set. **Ask where the page's class actually lands** — on the component's own element, or on an ancestor. Those two have opposite outcomes, and the second (inheritance from a nearer ancestor) cannot be fixed by specificity at all.
- **⚠️ TWO WAYS TO EXPRESS ONE INSET — `padding` AND A `max-width` REDUCTION — AGREE UNTIL A CAP BINDS, THEN DIVERGE BY THE WHOLE INSET.** *(21 Aug, the same pack.)* The masthead was padded and the content was reduced (`min(cap, 100% - 2 × gutter)`), which is the same left edge while the cap is slack. The moment the cap binds, the reduction is **absorbed** — `min()` takes the cap and the gutter simply stops applying — while the padding is still **added** on top of it. Measured: masthead ink and content aligned exactly at 1440 and sat 35px apart at 2300, on a value chosen so they would match. **Compute both sides the same way, or the agreement is a coincidence of viewport.** The same choice also decides where an absolutely-positioned child lands: `right: 0` resolves against the **padding box**, so a padded measure hangs a control outside its own ink.
- **⚠️ A CHECK THAT PASSES BECAUSE IT NEVER MEASURED THE THING IT NAMES — THE PRECONDITION GAP.** *(20 Aug, and it is the shape behind several faults in one pack, which is why it is stated as a family rather than as another example.)* An assertion names a state ("max scroll is unchanged **once the masthead has scrolled out of view**") but only measures the consequence, never the state. If the page never reaches that state the consequence is trivially true and the check goes green having tested nothing. **The measurement asserts the PRECONDITION first, then the claim.** Instances already in this file, all the same shape: `elementsFromPoint` outside the viewport returns an empty array, so a stacking probe is satisfied by `undefined` — assert the rect is on screen first; a `sliceBetween` whose end anchor is missing silently widens to the rest of the file — assert both anchors; a source lock reading prose instead of code — strip comments first.
  - **⚠️ AND IT BITES HARDEST ON A PROPERTY THAT HOLDS BY CONSTRUCTION.** When the invariance padding was deleted, max scroll became constant *because the masthead is content and changes no heights* — so there is nothing left to compensate and nothing left to get wrong. **That is precisely the property nobody thinks to check, and the construction is a paragraph of CSS anyone can edit.** Keep measuring it, and make it state its own precondition, or the day someone gives the masthead a height again the check will still be green.
- **⚠️ A MOCKUP ONLY EXERCISES THE GLYPHS SOMEONE TYPED INTO IT.** *(21 Aug, the masthead title.)* Descenders, diacritics and long strings are exactly what a ref does not test — its author writes a plausible label, it looks right, and the value tuned to it ships. `line-height: 1.02` came from TWO refs that agreed, and **two artefacts agreeing is not corroboration when they share a blind spot**: both drew titles with no descenders, so neither could show that the largest text on every page was being cropped. It reached dev.
  - **THE COROLLARY FOR VALUES READ OFF A REF:** a number tuned to the sample renders the sample correctly. Before taking one, ask what the real content can contain that the drawing does not — and **prefer a floor that holds for every string a user might have over a value fitted to the one that was typed**.
- **⚠️ WHEN A REPORT NAMES SYMPTOMS, SCAN FOR THE FAULT CLASS — DO NOT TREAT ITS ELEMENT LIST AS THE SEARCH SPACE.** *(21 Aug.)* A clipping bug arrived described as "the top breadcrumb bar — ScriptAlly and the page name, both clipped". Probing those classes would have found the breadcrumb WHOLE (1.5×, uncropped) and fixed nothing: the clipped "ScriptAlly" was the SIDEBAR wordmark sitting in the same band, and a third site — the masthead title — was not in the report at all. **Scanning every Playfair leaf for the PROPERTY found all three.** A reporter names where they were looking; the fault is wherever the declaration was copied to.
- **⚠️ `line-height: 1` IS ONLY EVER SAFE ON UPPERCASE-ONLY TEXT — ON MIXED-CASE PLAYFAIR IT CUTS THE DESCENDERS.** *(21 Aug. A correct rule applied to the wrong type, which is why it survived review three times.)* `line-height: 1` was RIGHT for the retired mono-uppercase band label: uppercase mono has no descenders, so a line box the size of the em is exactly the ink. The same declaration on Playfair rendering mixed case crops the `y` in "ScriptAlly" and in "Query Centre". **Minimum 1.3 anywhere Playfair renders mixed case**; a fixed height with `overflow: hidden` does the same damage by a different route, so **size a text container by its line box, never by a number that happens to fit most glyphs** — `min-height` plus padding where a row needs a nominal height.
  - **MEASURED ON DEV, THREE SITES:** the sidebar brand `.ws-bwm` (26px of ink in a 22px box), the masthead title `.wsh-title` (35 in 31, at 1.02× — a value taken from two refs whose drawn titles happened to have no descenders), and the folded bar `.wpg-mini-name` (22 in 19).
  - **⚠️ THE CHECK IS `scrollHeight === clientHeight` ONLY WHERE THE BOX ACTUALLY CLIPS — OTHERWISE IT IS THE WRONG INSTRUMENT, AND IT HAS NOW MISLED TWO PASSES.** On an `overflow: visible` box `scrollHeight` reports the union of the content box and anything spilling out of it, and **Playfair's ascent plus descent exceed any `line-height` under ~1.15** — so a sweep written that way reports *every* tight-leading Playfair element on the marketing pages as cropped while nothing is cropped at all. Measured 24 Aug: 18 "failures" on the landing, **zero real**. The reading only means "crops its OWN content" when the element has `overflow: hidden`/`clip` or a fixed height. **The instrument that is always right is INK against a CLIPPING ANCESTOR**: take the union of the element's `Range.getClientRects()`, walk up for the first ancestor whose `overflow` is not visible, and ask whether the ink is outside its box. Do both where the box really clips, and **collect every offender rather than throwing at the first** — this kind of declaration gets copied, and the pack that named two sites had three. ⚠️ **AND KEEP THE `line-height < 1.3` READING AS A CENSUS, NEVER AS A FAILURE.** Seven marketing elements sit below the floor on purpose and each was measured (`mk-wordmark` 1.00, `mk-mission-main` 1.02, `mk-dn` 1.10, `H2` 1.18/1.20, `mk-turn-b` 1.22, `H3` 1.25). Printing the set and comparing it to the known one catches a NEW offender without going red on the sanctioned ones.
  - **⚠️ AND THE PROBE MUST SAMPLE A STRING THAT HAS A DESCENDER.** "Dashboard" has none and passes on a clipped box; "Query Centre" does not. The ratio check exists for the same reason: a box that does not clip TODAY because of the words in it will clip the day the page is renamed.
  - **⚠️ A SYMPTOM REPORT NAMES A PLACE, NOT AN ELEMENT.** This arrived as "the top breadcrumb bar — ScriptAlly and the page name, both clipped". The breadcrumb runs at 1.5× and is whole; the clipped "ScriptAlly" is the SIDEBAR wordmark sitting in the same band. **Scan for the property, do not grep for the described class** — a probe list written from the description would have fixed a page that was not broken.
- **⚠️ WHEN A MEASUREMENT IS SLOWER THAN ANOTHER SESSION'S EDIT LOOP, NO AMOUNT OF REBUILDING WINS — THE TREE SPLIT IS NOT HYGIENE, IT IS THE ONLY WAY THE RUN COMPLETES.** *(20 Aug, the masthead pack's step 4.)* `dist/` and `src/` are shared across every session in a checkout, and `bundleGuard` refuses to measure a bundle whose sources changed after it was built — correctly, since the alternative is reporting your own edit as absent. A Playwright run over ten pages takes minutes; another session editing `src/` makes the bundle stale inside that window, and **every case after the first dies at sign-in.** Rebuilding and retrying is a race lost by construction.
  - **THE NUMBERS, BECAUSE "IT HELPED" UNDERSTATES IT:** the same six measurement files were UNFINISHABLE in the shared checkout and ran **12/12 in 3.9 minutes** in a worktree. Not slower — unwinnable.
  - **THE SHAPE:** `git worktree add --detach ../ScriptAlly-<task> HEAD`, copy the working changes across, symlink `node_modules`, build and `vite preview` on its own port, point the harness at it with `SA_E2E_BASE_URL`. **It is a MEASUREMENT environment — commits still come from the primary tree**, so direct-to-main is unchanged. `.env.local` and `tests/e2e/.auth/` have to be copied (both gitignored, both the dev-only harness account); say so in the report, and delete the second copy when the worktree goes.
  - **⚠️ AND CHECK FOR COLLISIONS BEFORE COPYING ANYTHING IN.** `git diff --name-only <your-last-commit>..HEAD -- <your files>` — if the other session has committed to a file you are about to overwrite with your working copy, you would silently destroy their work.
- **⚠️ ON A PAGE WHERE NOTHING SCROLLS, `position: sticky` DOES NOT IDLE — IT CLAMPS.** *(20 Aug, the mini bar's `top` offset.)* Everyone holds sticky as "it pins the element when it would otherwise scroll away"; what it actually does is **clamp the element into the region at or below its `top`**. Those are the same thing on a scrolling page and they are not the same thing on a fill page, where there is no scrolling and the clamp is the ONLY behaviour left. Giving the control row `top: 51px` — to clear the mini bar above it — therefore pushed the row DOWN 51px on every fill page, where no mini bar renders. **The signature is a fold that reclaims less than it should:** Calendar's masthead collapsed 118px and the content below it rose 67, the missing 51 being a gap held open for an element that was not there.
  - **⚠️ `top: 0` HIDES THIS RATHER THAN FIXING IT** — clamping to 0 is a no-op when the natural position is already 0, which is why the row carried a sticky nobody noticed for two packs. The honest statement is `position: static`: a sticky on a page that cannot scroll claims a behaviour that cannot occur, and **a dead claim is how the next reader is misled** into adding an offset to it.
- **⚠️ SCROLL ANCHORING IS A BROWSER BEHAVIOUR THIS APP NOW DEPENDS ON — `overflow-anchor: none` IS NOT A FREE FIX.** *(20 Aug, the mini bar.)* The bar takes its full height in FLOW the moment a page sticks (42.7px since the height started deriving from its type — it was 51), so everything below it moves down and `scrollHeight` grows by the same. Nothing lurches only because the browser raises `scrollTop` by the identical amount: measured on Contact list, a 10px wheel tick takes `scrollTop` 0 → 53 and a content landmark moves exactly 10px. **Adding `overflow-anchor: none` anywhere on an ancestor of `.wpg-scroll` — a common reach when chasing an unrelated flicker — makes content lurch half a bar-height down on the first tick of every scrolling page, and it reads as a mini-bar bug.** `stickyRow.measure.ts` fails first and names the cause; the stylesheet carries the warning where the `none` would be typed.
  - **AND IT IS SINGLE-ENGINE EVIDENCE.** Chrome and Firefox anchor; Safari's behaviour differs; the harness only ever asks Chromium. The measurement proves the property where it is taken and not that it holds everywhere — the honest reading of any one-engine result, and worth remembering before it is quoted as settled.
- **⚠️ A DECLARATION CAN APPLY CLEANLY AND HAVE NO EFFECT — AND COLLAPSING MARGINS ARE THE CHEAPEST WAY TO GET THERE.** *(20 Aug, the in-flow masthead's sticky control row. Same family as `transform` isolating a `mix-blend-mode` group: the rule is valid, it matches, the browser honours it, and the thing you wanted does not happen.)* The sticky row tightens its padding when it anchors, which takes 4px out of its flow height and therefore out of `scrollHeight` — the shrink/clamp/un-shrink cycle documented under the header rules. The compensation was written as **`margin-bottom: 4px`**, which is exactly right in arithmetic and worth nothing in practice: **adjacent siblings' margins COLLAPSE**, so it was absorbed by the following element's `margin-top` and the row's contribution fell by 4 anyway. **`padding` cannot collapse; `margin` can.** Any compensation that has to preserve a box's contribution to a scroll height must be padding, a border, or a rule inside a flex/grid container, where collapsing does not happen at all.
  - **⚠️ IT IS INVISIBLE TO EVERY SOURCE-READING CHECK, AND THE UNIT LOCK PASSED.** The lock summed `2 × padding + margin-bottom` off the stylesheet and got 24 = 24 — correct arithmetic about a page the browser does not lay out that way. **A compensation is verified by measuring the box, never by adding up its declarations.**
  - **⚠️ AND IT HID BEHIND A BIGGER FAULT.** A stale `--wpg-reclaim-pad` was adding 99px in the same state change, so the −4 was invisible until that was removed. **When one measurement is wrong by a large number, fix it and MEASURE AGAIN before concluding anything about the small ones** — the second reading is where the subtle fault lives.
- **⚠️ MOTION TRAP — a card sits ~7px out of place after a reflow, looking like a layout bug.** *(Stated symptom-first on purpose: the symptom points away from the cause, so anyone hitting this will chase it through layout code first and find nothing wrong there.)* **Cause:** an entrance animation with `fill-mode: both` outranks inline transforms, so a FLIP offset is discarded and the keyframe's own offset wins instead — `transform: translate(200px,150px)` on a card holding a finished `rise` computes to `matrix(1,0,0,1,0,7)` (browser-measured, 29 Jul).   - **⚠️ AND WHERE THE ANCHOR NOW SPANS THE SEAM, THE LOCK FOLLOWS THE BEHAVIOUR, NOT THE FILE.** `openFlowCards([card])` became `host.openFlow(card)` in the session plus `openFlow: (c) => openFlowCards([c])` on the page: asserting only the session's half would pass on a page that had quietly stopped mounting anything, which is the failure the lock exists for. Assert both halves — and **where a half is no longer expressible in source at all, say so rather than silently narrowing what the lock covers.** The dock cursor's "read the board as it WAS" is now closure capture rather than statement order; no source lock can see that difference, so the lock names it and hands it to the rendered check.
- **⚠️ A LAYOUT CLAIM IS VERIFIED BY MEASURING THE RENDERED PAGE — AND "LANDED IN CODE" IS NOT "LANDED ON THE PAGE".** *(15 Aug — the fourth of the four, and the one the other three cannot substitute for. `npm run e2e` against the deployed dev site is the instrument; `tests/e2e/measure.ts`'s `openRoute` + `liftMotionSuppression` are the entry points.)* **The worked example is the smallest possible and the most alarming: `repeat(auto-fit, minmax(0, 1fr))` on the stat block.** It was written to make one stat span and two share, a unit lock asserted that exact declaration, the lock was green, and the deployed page resolved the block to `195px 195px` **followed by a hundred-odd phantom `0px` tracks** — auto-fit with a zero minimum has no reason to stop. It *rendered* correctly by luck. **The lock could never have caught it, because the lock asserted the declaration that was itself the fault** — which is the general case: a source-string lock proves the code was written, not that it ran, and a CSS lock proves a rule exists, not what the cascade and the box model do with it. **The same pass produced three more that only measurement found:** the record column resolving to `162px` (then `352px`) while the grid template read correctly; the motif intersecting the close control at 1920 but not 1440, because a static `.tdk-x` takes no z-index; and a rail hover swap that was *already working* while a screenshot said otherwise. ⚠️ **SO STATE WHICH KIND OF VERIFICATION A CLAIM HAS.** "Landed" for something covered only by unit tests is the report that has misled this project most: six of eight rows in one state list were true in code and unproven on a page. Write `landed (code + unit)` and `landed (measured at 1440/1920)` as different things, and **measure at more than one width** — a law that holds at exactly one width is a coincidence, and both faults above appeared at one width and not another. ⚠️ **AND THE HARNESS IS NOT THE PAGE**: `reports/`-era harnesses were wrong four times in a day, which is why the instrument opens the deployed site signed in and asks the browser (see the Playwright note under Conventions, including its one blind spot — the scrollbar). ⚠️ **AND A MEASUREMENT OF AN ELEMENT THAT IS NOT ON SCREEN IS NOT A MEASUREMENT — CHECK THE RECT IS IN THE VIEWPORT BEFORE ASKING WHAT OWNS ITS PIXELS.** *(16 Aug — the fifth in this family and the most dangerous shape yet, because it passes by returning NOTHING.)* `document.elementsFromPoint()` outside the viewport returns an **empty array**, so `expect(stack[0]).not.toBe("body")` — written to prove a control was not sealed behind an overlay — was satisfied by `undefined`. The control was at `y 1271` in a `1000px` viewport, and the assertion guarding it reported success. The other four vacuous shapes at least evaluated something; this one asserts about an element the browser never looked at. **Assert the rect first** (`y + h <= viewport.h`), then ask what is at its centre. The general form: any probe that takes COORDINATES needs the coordinates proved on screen before its answer means anything. ⚠️ **The same pass produced the same claim-versus-reality shape in a comment**: `paneJourney.css` said the summary and footer were "siblings of the scroller" while `PaneJourney.tsx` rendered them as children — the file describing the intent while the component did the opposite, which is the commit-message fault wearing a stylesheet's clothes. Only the measurement told them apart.
- **⚠️ EVERY WORKSPACE PAGE STAYS MOUNTED, SO A HARD-CODED `id` IS A DUPLICATE THE MOMENT A SECOND SURFACE RENDERS THE SAME COMPONENT.** *(23 Aug — recorded as a GENERAL hazard on Nick's instruction, after the third session it has bitten. Its intended home is the harness pack's flag 4; this is the standing record until that report exists.)* The known half of this trap is that `document.querySelector` can return a **hidden page's zero-sized copy** — which has produced a false finding, a seven-minute `locator.hover` hang, and an "unclickable" button hunt. **The half that is new is the id.** `TaskPaneBody` renders `id="s-unit"`, `id="s-when"`, `id="s-expect"`, `id="s-remind"`; mount that component on a second page while the first is alive and the document holds **two of each**. Two consequences, and the first is the one that looks like a feature bug: `document.querySelector('.tpn #s-unit')` returns the FIRST match, so a "jump to the missing answer" scrolls a page the writer cannot see; and duplicate ids are invalid HTML, so any `aria-labelledby` or label-`for` resolving by id becomes ambiguous. **Scoping the query to a ref fixes the first and NOT the second** — the ids are still duplicated, and the fix for that is an `idPrefix` prop defaulting to today's values so the original page stays byte-identical. **The rule: before a component with a hard-coded `id` gains a second mount, give it an id prefix.** Grep for `id="` in any component about to be reused, and remember that in this app "reused" means "rendered on two routes", which is the normal case rather than the exotic one.
- **⚠️ A COMMIT MESSAGE STATES WHAT ITS DIFF DOES. VERIFY THE CLAIM AGAINST THE DIFF BEFORE WRITING IT.** *(15 Aug — the third of the three, and the most expensive per word, because a commit message is the one artefact nobody re-checks.)* **The worked example: `053884f` ("Phase 4 — page strips back to the control bar") states that it removed "the four count pills" and that `taskStats` "survives in `todoGroups`, pure and locked, **unmounted**". Both halves are false.** `.tdg-stats` — four chips rendered from `taskStats(boardCols, …)` — is present in `ToDoPage.tsx` at that commit's parent, at the commit itself, and stayed mounted for six commits afterwards; `git show 053884f -- src/components/todo/ToDoPage.tsx | grep "^-"` contains **zero** lines touching either identifier. What it actually removed was the eyebrow, the `#All` tag dropdown, `Work the list` and `renderTools`. **The cost is not the wrong pills — it is that a whole session was spent believing the page had already been stripped**, and the disbelief only arrived when someone looked at the live page and could not reconcile it. **A test that is wrong goes red; a commit message that is wrong is read as fact for as long as the repo lives.** In this codebase that is worse than average, because messages here carry the *reasoning* and are quoted forward into the next pack's prose — so one false claim propagates into every document written on top of it. **The mechanical rule, which costs seconds: before writing "removes X" / "unmounts Y" / "retires Z", run `git diff --cached -- <paths> | grep "^-" | grep X` and read the result.** If the identifier is not in the removed lines, either the claim is wrong or the change is incomplete — and both of those are things to find out now rather than three sessions later. **The same check applies to a claim about the WHOLE tree** ("nothing else calls this"): grep for it, and say what you grepped. ⚠️ **And a claim about what is MOUNTED needs a reachability check, not a definition check** — `grep -c` finds a function; only tracing its callers to a rendered root tells you whether it runs. ⚠️ **WHEN A SYMBOL LOOKS DEAD, TRACE IT TO A RENDERED ROOT BEFORE ACTING — IN BOTH DIRECTIONS.** *(Three times in one week a reachability question changed the answer: the dock queue, the two primaries, then the row/reel cluster.)* **Downward**, so you do not delete something a live path still reaches; **upward**, so you do not spend a session hardening something nothing renders. Both failures are silent and both are expensive — the row/reel cluster held four buttons and thirty-eight test cases, all green, none of them reachable, and a whole reconciliation session was spent believing a page change had landed when the code implementing it had no caller. **The cheap mechanical version is a fixed-point sweep**: list every component-level `function X(`, count references outside its own body, mark the zero-reference ones dead, repeat until nothing new appears — it took the honest cluster from the 7 symbols that looked dead to the 12 that were, and separately surfaced 10 more that had been dead beforehand. **Do the sweep before proposing the scope, not after**, and state which are the cascade and which were already dead — they are different decisions.
- **⚠️ WHEN A PASS INTRODUCES A REPLACEMENT, THE THING IT REPLACES IS DELETED IN THE SAME COMMIT — AND NEAR-IDENTICAL SIBLINGS ARE COMPARED BY DIFF, NEVER BY READING.** *(25 Aug, the packages band's two ghost cards — the THIRD instance in one build, which is what makes it a rule rather than an anecdote.)* A replacement that is **added** leaves the original reachable; only a replacement that is **swapped** retires it. The three: `#/pkg-lab`'s cascade (six unreachable views, 2,223 lines, kept alive because one dev route still mounted them); the import's two auto-create blocks (a retired path surviving beside the flagging that replaced it); and two hand-written `Build another package` ghosts, rendered back to back, both wired to `onNewPackage`.
  - **⚠️ NEAR-IDENTICAL COPY IS THE CAMOUFLAGE, AND IT DEFEATS READING SPECIFICALLY.** The two ghosts differed by ONE WORD — *"A different letter, a different length of synopsis."* against *"A different letter, a different synopsis."* — and by a size (54px against a 44px chip). A reader scanning the JSX takes the pair as one block, because that is what the eye does with two adjacent paragraphs saying the same thing. **`diff` the two candidates rather than reading them**; the one-word difference is invisible in prose and unmissable in a diff.
  - **⚠️ AND THE PAIR CARRIED A DUPLICATE `id`.** Both slots rendered `id="pkg-ghost"`, so the document held two — the invalid-HTML half of the hard-coded-id hazard above, arriving by a route that rule does not cover: not a second MOUNT of one component, but two components hand-written with the same literal. **When you find near-identical siblings, check their ids before deleting either.**
  - **THE DETECTION SIDE IS ALREADY HERE** — the fixed-point reachability sweep in the entry above finds what survived. This entry is the **authoring** side, which is cheaper: it stops the thing existing. The sweep found the ghosts only because a rendered-element count in two data states put `ghostCards: 2` next to `realCards: 2`; reading the component had not, across several passes.

- **⚠️ A TEST MUST CALL THE FUNCTION WITH AN INPUT THE SYSTEM CAN ACTUALLY PRODUCE.** *(15 Aug — the sibling of the comment-stripping rule above: same family, same cause, and the failure is silent in the direction that costs most.)* `journeyMaterials` had a branch giving an R&R its two pre-ticked rows, and a unit test asserting them — `rows("send", "revise_resubmit")` — that **passed for the life of the feature while the rows had never once rendered.** The journey's only call site passes `cardBucket(card)`, and an R&R's bucket is `decide`, which sat in the function's no-materials guard. The test supplied `"send"`: a bucket **no R&R card can produce**. **A test that hands a function an argument its callers cannot is testing a function nobody runs** — it is exercising the wrong artefact, exactly as a source-string lock reading prose instead of code does. **The fix is to DERIVE the input from the thing that really builds it** (`journeyMaterials(cardBucket(rr), …)`, not `journeyMaterials("decide", …)`) — a literal is the same fault one step along, going green the day the producing mapping moves. ⚠️ **The tell is a hand-written argument to a function whose real caller computes that argument**; when you type a bucket, a status, a route or a task type into a test by hand, ask which function computes it in production and call that instead. The three reconciliation invariants in `agentList.test.ts` are the pattern done right: they assert two derivations **against each other**, never against literals.
- **⚠️ QUERYING TWO ELEMENTS SEPARATELY CANNOT DETECT THAT THEY RENDER AS ONE RUN — ASSERT THE PARENT'S TEXT OR THE GEOMETRY, NEVER EACH CHILD'S.** *(21 Aug, the packages materials band; the sibling of the negative-space entry below, and the cheapest of the whole family to hit.)* A source line and a usage line were `<span>`s where the ref had `<div>`s, so `margin-top` applied to nothing — **vertical margin is inert on an inline box** — and the page read **"TextIn 1 package"**. Eleven assertions passed. They had to: a probe does `el.querySelector(".src").textContent` and `el.querySelector(".use").textContent`, and **each string was correct**. The fault was never in either element; it was in the line they made together, which no per-element query can see. Only the screenshot showed it.
  - **THE CHECK THAT WOULD HAVE CAUGHT IT:** read the PARENT's `textContent` and require the separator you expect (a newline, or a known join), **or** compare the two children's `getBoundingClientRect().top` and require them to differ. Both ask about the relationship; the per-child query asks about neither.
  - **THE GENERAL FORM, and it reaches well past CSS:** *a measurement of the parts is not a measurement of the whole.* The same shape is a stat block whose tracks each resolve correctly while the grid grows a hundred phantom columns, and a header whose mark and title each measure fine while they overlap. **When the claim is about arrangement — order, spacing, adjacency, containment — the probe must read something that exists only in the arrangement.**
  - **AND IT IS A REASON TO KEEP LOOKING AT THE PAGE.** The measurement harness is the instrument for "is this correct"; it is not a substitute for opening the screenshot once per phase. This class is invisible to it by construction, and a phase that never renders an image will ship it.
- **⚠️ ASSERT WHAT MUST NOT HAPPEN, NOT THAT NAMED THINGS EXIST — THE NEGATIVE-SPACE CHECK.** *(21 Aug, the account-settings overlap gate; this is the entry to point a future session at when it asks what "measure, don't assert" means in practice.)* Every positive check names the elements it knows about, which is exactly the set that is already correct in the author's head. **Three real faults in one build were all invisible to positive checks and all caught by one negative one**: a header illustration that flew to the bottom-right of the PAGE while the assertion `plateHasIllo` measured `true` (the element genuinely was in the plate's subtree — it was `position: absolute` with no positioned ancestor); an aside whose text sat underneath its own mark because `height: 100%` resolved against a content-height frame; and a card body filling 213px of a 520px card, every `flex: 1` in the chain applying and doing nothing. Nobody would have written a check for any of them. **"No two pieces of text may occupy the same pixels, and no illustration may occupy a reader's" catches all three without knowing about any of them.**
  - **THE SHAPE:** collect the bounding boxes of every visible text LEAF and every illustration in the region; assert no pair intersects. **Leaves only** — a parent's box contains its children's by construction and inline siblings share a line box, so comparing those reports overlap on a correct page forever. Give the intersection a 1px tolerance so sub-pixel edges meeting is not a failure.
  - **⚠️ AND IT NEEDS A FLOOR ON WHAT IT FOUND, OR A CLEAN RESULT MEANS "I MEASURED NOTHING".** Zero boxes yields zero overlaps and passes. This is the same vacuous family as the off-screen `elementsFromPoint` above, and it is the failure mode of *every* negative check: the assertion is satisfied by an empty set. Assert the population first (`expect(boxes.length).toBeGreaterThan(n)`), then assert the property. The settings gate reports 15–65 boxes per scan for exactly this reason.
  - **RUN IT UNDER STRESS, because growth must PUSH layout and never overlap it.** Repeat every scan with the longest realistic content injected — a 38-character double-barrelled name, every helper note doubled. A layout that only holds at the content you happened to test is a coincidence.
  - **⚠️ IT IS THE COMPLEMENT OF THE STRUCTURAL FIX, NOT A SUBSTITUTE FOR IT.** The same build moved every illustration into the flow (content → flex spacer → foot row) so overlap became structurally impossible; the gate then had nothing to find. **Prefer making a fault impossible to proving it absent** — an absolutely-positioned mark that measures clear today is one content change from not being. The gate exists to catch the next person who reaches for `position: absolute`.
- **⚠️ COPY ASSERTS ONLY WHAT THE CODE DOES TODAY — never the intended behaviour, however certain the intention.** *(21 Aug, and it is a FAMILY this repo keeps rebuilding under new names.)* The instances: the manuscripts plate's `Added {date}`, derived from earliest activity, which on an imported manuscript is a first-query date wearing the wrong label; a security section's `Last changed {date}` for a password, which Firebase does not expose at all; and a settings timezone note reading *"Dates, reply windows, and 'how long ago' are all worked out in this timezone"* when nothing read the stored zone — **written into a copy table by the person who knew the field was unwired**, which is how the class survives review. **The tell is copy specified alongside a feature rather than after it.** A sentence describing what a control WILL do reads identically to one describing what it does, and only the second is safe to ship.
  - **THE COST IS ASYMMETRIC AND THAT IS WHY IT MATTERS.** A missing sentence is a gap someone notices and asks about. A false one is disproved by the reader in a single glance — at a date, at a timezone, at a page full of `en-GB` dates under a setting claiming `MM/DD/YYYY` — and what they learn is not that one line is wrong but that the app's copy cannot be trusted.
  - **THE MECHANICAL GUARD:** before shipping a sentence that names a behaviour, grep for the thing that performs it. If the answer is "nothing reads this field yet", the copy says so or says nothing. **`accountPrefs.TZ_HELPER` is the worked example of saying so** — it states that the zone is stored for work not yet switched on, which is true, useful, and impossible to disprove.
  - And where a figure is a placeholder nobody has confirmed — `DELETION_WINDOW_DAYS` was the literal string `"[30]"` for months — **ship without the number rather than with the brackets or with a guess**. Turning a placeholder into a commitment in a privacy notice is a business decision, not a formatting fix. (Confirmed 30 days on 21 Aug; the constant is now a number and settings and the policy read the one value.)
- **⚠️ A LOOKAHEAD AFTER OPTIONAL WHITESPACE IS NOT A FILTER — EXTRACT THE VALUE AND COMPARE IT.** `width\s*:\s*(?!100%)` **matches `width: 100%`**: `\s*` backtracks to zero width, so the lookahead is tested against the SPACE rather than the digits, and every value passes. The same shape has now bitten twice — `top\s*:\s*(?!0)` flagging `top: 0` in `workspacePageGrid.test.tsx`, and `width\s*:\s*(?!100%)` in the width-chain lock **written three rules below the comment describing the first one**. Reading the paragraph is not protection; the pattern looks correct and the failure is silent in the permissive direction. **The fix is always the same: capture the value, trim it, and compare in code** (`["100%","auto","0"].includes(v)`), which says what is meant and cannot be defeated by backtracking. Applies to any "must not be X" written as a regex, not just CSS.
## Header types — canonical

*(pinned chrome; refs `174-pinned-chrome-options.html` option C + `175-sticky-masthead-chevron.html`. **This block replaces every earlier masthead rule** — collapse-on-engagement, the mini bar, the settle/Hide coexistence and every per-page arrangement.)*

A page has a **single primary scroller** if exactly one element scrolls the page's own body — the scroll row, or one internal zone. Panes that scroll independently of each other are not a primary scroller.

**Type A · Pinned.** Pages with a single primary scroller. The masthead and control row are one sticky slab at `top: 0`, with one full-width base hairline and one shadow on pin. The slab settles when the primary scroller scrolls: mark 52→34, title 30→22, description folds, paddings tighten. **No Hide. No chevron. No fold.**

**Type B · Static.** Pages with no single primary scroller. The masthead sits in flow, not sticky, and never settles. **Hide** folds it to a chevron badge straddling the window's top border. **No sticky. No settle.**

No page may be both. No page may be neither. No page may opt out.

**The wash belongs to every masthead, both types** (24 Aug) — a parchment band, `--mast-wash-top` → `--mast-wash-bottom`, on the slab. It was briefly scoped to Type A on the reasoning that it compensates for content passing beneath; that is a fact about behaviour, not about what a masthead is, and it excluded Query Centre and Manuscripts. **The toolbar is not the header**: it travels inside the slab so it pins, and keeps the page's own `--ws-window` on a full-bleed band of its own — the colour change between the two is the only boundary, with one hairline and one shadow at the base of the pair. **The toolbar does NOT retract on scroll** — it was built to option C, measured, and withdrawn; see the note on compensating a CSS transition below for what it cost and why.

**The assignment, measured:** Type A — Analytics, Contact list, Discover, Comparable titles, Submission packages, To-do, Calendar, Noteboard. Type B — Query Centre, Manuscripts. **Type is a property of STRUCTURE, not of today's content**: Calendar is Type A even at a viewport where its zone does not overflow, because it HAS one primary scroller and would settle if it had anything to settle for.

- **⚠️ THE TYPE IS ONE DERIVED BOOLEAN, AND `fill` IS NOT IT.** `fill` describes the LAYOUT — the row does not scroll, the panes do; the type describes the CHROME. The Tasks family is `fill` and Type A; Query Centre is `fill` and Type B. Conflating them is what produced a page with both a settle and a Hide. A page is Type A if it is not `fill`, or if it NAMES its primary scroller through `settleOn`.
  - **⚠️ AND THE DECLARATION CANNOT BE REPLACED BY DISCOVERY.** "The single element that currently overflows" finds exactly one on Query Centre — one pane happens to hold enough to scroll — and concludes it has a primary scroller. It has none. The fact is the page's intent, and intent is not in the DOM's behaviour. `data-wpg-settle` and `data-wpg-type` put it there so a lock can partition ten pages without naming any of them.
- **⚠️ A PORTAL OUTLIVES ITS PAGE UNDER A DISPLAY-TOGGLING SHELL.** The fold's chevron is portalled to the window's wrapper, which is the SHELL's and shared; the workspace keeps every page MOUNTED and toggles `display`. So a folded page went on rendering its badge into that shared host after the reader navigated away — measured: fold Query Centre, open Comparable titles, and QC's chevron floats at y=100 over a page that has no fold at all. **Anything portalled to a shell-level host must also ask whether its page is the one on screen.**
  - **ONE SLAB.** Masthead and control row are one `position: sticky; top: 0` block with ONE full-width hairline at its base and ONE shadow, the shadow appearing only when pinned. What it replaces is what the ref calls *the clash*: two independent stickies, the masthead's rule stopping at its own MEASURE while its shadow ran full width, and a second line-plus-shadow a few pixels below. **The slab is the scroller's only sticky element, so every `top` is 0 by construction** — the strongest form the "no offset encodes another element's height" rule has taken.
  - **⚠️ THE SETTLE SHRINKS THE CHROME, AND SHRINK IS THE DANGEROUS DIRECTION.** Mark 52→34, title 30→22, description folds, paddings 24/18→13/10 and 14/14→0/12: ~62px out of `scrollHeight` the instant the page pins. The mini bar was safe because it GREW. A page overflowing by less than the settle would be clamped to 0, un-settle and cycle.
  - **⚠️ AND THE COMPENSATION IS A SPACER, NOT SCROLLER PADDING.** Padding held max scroll constant and left the flow to collapse — measured, a 10px wheel tick moved a content landmark **67px**. Scroll anchoring does not absorb it: it is not content arriving above the anchor, it is the anchor's own offset shrinking. A box between the slab and the content does both jobs, because the slab's loss and the spacer's gain are one number. **The point of settling is that a PINNED slab uncovers 62px that was behind it; letting the flow collapse as well reveals the same 62px twice.**
  - **⚠️ THE GAP LIVES IN THAT SPACER, NOT AS A MARGIN ON THE SLAB.** With `margin-bottom: 16px` still on the slab, max scroll went **1918 → 1934** on every settle: the margin COLLAPSED with the content's own at rest and stopped collapsing the moment the spacer between them gained height. `--wpg-chrome-gap + --wpg-reclaim-pad` in one box cannot collapse.
  - **⚠️ THE RESTING HEIGHT IS ONLY READ WHEN NOTHING IS ANIMATING, and this is the subtle one.** `scrollTop <= 2` is true again while a settled slab is still EASING open, so capturing then records a half-settled box as the rest height and the next settle's reclaim is short by whatever the transition had left to run. Measured: a scroll landing on 4px moved a landmark **59px** — the whole settle paid by the reader's eye, on a compensation that worked perfectly two ticks earlier. Guard: `getAnimations({ subtree: true })` empty. **THE SUBTREE**, because the slab's own box does not transition — the masthead's padding, the mark and the title do, and the slab merely follows.
  - **⚠️ THE FOLD'S CHEVRON IS A SIBLING OF THE WINDOW, NEVER A CHILD.** `.ws-window` clips (`overflow: hidden`, 16px radius), so a child could never sit half outside it however positioned. `.ws-winwrap` takes the window's slot and the grid PORTALS the badge into it. **A constant is not worth a dependency edge** — importing the wrapper's id from `WorkspaceShell` made a leaf component depend on the whole shell, which transitively imports Firebase, and three unit suites stopped LOADING with `auth/invalid-api-key`. It lives in `shellSlots.ts`, which imports nothing.
  - **⚠️ "THE BORDER RUNS UNINTERRUPTED" MEANS NOTHING CUT IT, NOT THAT IT IS VISIBLE UNDER THE BADGE.** The badge is opaque and its centre sits on the line, so for 38px the line is covered — that is the drawing. The lock samples the top edge and asserts the WINDOW's own box occupies every pixel, and that the `::after` overlay still spans `inset: 0`.
  - **⚠️ THE INVARIANCE PADDING IS `:not(.wpg--fill)` STILL** — a fill page has no scroll to clamp, and `.wpg--fill > .wpg-scroll` is a flex column where `padding-bottom` comes out of the content box and shoves the panes up.
- **⚠️ THE GAP UNDER THE HEADER IS 44px, AND IT IS A VALUE — the half-height rule was offered and REJECTED.** "Half the header's height, rounded" gives 64 from the 128px plate and would move the gap with it for free; **44 is deliberately tighter than half and was chosen over it.** Recorded because that tidiness is exactly what someone later "restores", which would add 20px under every header in the app. Rest geometry: **plate 128 · illustrated mark 88 · title Playfair 38/600 (solo 40) · gap 44**; the working state is untouched at 52/mono-label/mark-gone/`#f2ede7`/35.
- **⚠️ THE GAP IS THE GRID'S ALONE — a page that adds its own top padding defeats the token without contradicting it.** The once-only rule (`.wpg--tools` zeroes the scroll row's copy) was correct and locked, and it guards the wrong half: nothing was watching a page padding the FIRST thing in its scroll row, which is indistinguishable from the gap and simply adds. Measured: Comparable titles rendered **92** against a 70px token (`.ct-pagebody`, +22) and Discover **154** (`.dv-hero`, +84, the ref's value taken from a standalone card with nothing above it), while every page that adds nothing measured exactly 70. **It is not a toolbar thing** — Manuscripts has no toolbar and was clean, To-do has one and was not; the only predictor is whether the page pads its own first row. **A FRAMED box's padding is its own** (`.pkgw-strip`'s 11px sits inside a bordered strip whose edge is at the gap), which is why the check reads the PIXEL — `gapAudit.measure.ts` — rather than the source.
- **⚠️ A CONVERTED PAGE'S `flex: 1; min-height: 0` CHAIN NEEDS A FLEX PARENT, AND `.wpg-scroll` IS A BLOCK.** A page written as a viewport-locked column says `flex: 1; min-height: 0` all the way down; under the workspace grid the parent is the scroll row, so both declarations apply to nothing and the page's own height arithmetic silently stops being load-bearing. **`flex: 1 1 0%` with `min-height: 0` is the worst case: it contributes ZERO to a content-sized container and then has no free space to grow into, so it computes to EXACTLY 0** — with every element inside it mounted, styled and correct. Measured twice: `.tpl-cols` (696px of overflow through a frame whose lock says it never scrolls) and `.f12-body` (Query Centre's whole journey body 0px tall, holding a 167px step stack). **Both hid behind content that happened to size the container**, so a source scan finds neither — Tasks' columns had height of their own, Query Centre's browsing state was propped up by the query list, and only the journey, which hides the list, had nothing left. **The fix is the grid's `fill` prop** (`.wpg--fill > .wpg-scroll { display: flex; flex-direction: column }`), opt-in because on a flowing page a `flex: 1` child would start filling the row instead of flowing past it. **The tell is a page that scrolls where its spec says the panes do** — same fault, milder symptom. Locked by measurement, not source: the acceptance matrix fails any box in a scroll row that measures 0 while holding rendered content.
- **⚠️ A HARNESS THAT SUPPRESSES ANIMATION CANNOT EXERCISE ANY FLOW THAT TEARS DOWN ON `animationend`.** `animation: none` does **not** fire `animationend` — so a takeover whose exit is driven by that event arms its exit class and then never leaves, at any timing, looking exactly like a broken exit. This cost time twice in one session on the same stylesheet: once reporting `animationName: none` on a class whose only job is to run an animation ("the motion is dead" — it was not), and once reporting that Escape did not close the Query Centre journey (it does). **Suppress for static geometry; lift it and WAIT for any test that changes state.** `Queries.tsx` already carried the warning in prose, which did not help — the harness is a different file.
- **⚠️ A `ResizeObserver` ON A SCROLLER SAYS NOTHING WHEN ITS CONTENT GROWS.** It fires when that element's own box changes; `scrollHeight` growing because children arrived inside it is not a resize of the scroller. So anything derived from "is there content below" is computed once at mount and then never again on a page whose data loads asynchronously — **measured: Query Centre reported no bottom fade with 729px beneath the fold while every synchronously-rendered page was correct**, which is the shape that survives a whole pass unnoticed. **Observe the direct CHILDREN as well, and re-sync that list with a `MutationObserver` on `childList`.** Anything derived from `scrollTop` alone is immune — which is why the header state was right and only the fade was wrong.
- **⚠️ CSS GRID AUTO-PLACEMENT NEVER OVERLAPS — two items share a cell only when BOTH are explicitly positioned.** Adding an explicitly-placed overlay (`grid-row: 3; grid-column: 1`) to a grid whose other rows are auto-placed does not stack them: the auto-placed item is pushed into an **implicit new column**, and the grid silently grows sideways. Measured when the scroll hems landed: the header rows read **688px of right margin against another page's 449**, varying with the viewport, on nine of ten pages. **Declare `grid-template-columns` and give every participating row its `grid-column`** — on all of them, not just the newcomer; removing it from one takes that row out of the column.
- **⚠️ AN INTERSECTIONOBSERVER FIRES ONLY ON A *CHANGE* OF INTERSECTION, SO A MISSED EVENT IS PERMANENT.** A sentinel-and-observer is the wrong shape for "is this scroller at the top": if the callback is not delivered — because the sentinel was laid out after the observation began, or resized, or never left the box — nothing ever corrects it, and the state stays wrong for the life of the page. **Derive the state from the value itself**: `scrollTop > 2`, read on scroll, rAF-throttled, written only when it differs, with a `ResizeObserver` re-evaluating it. A derived reading cannot go stale; an event you did not receive can.
  - **⚠️ AND THE COMPANION TRAP: OPENING DEVTOOLS DOCKED SHRINKS THE VIEWPORT AND INFLATES EVERY OVERFLOW READING.** Manuscripts measured **267px** of overflow with the console docked and **42px** undocked — 62px of difference, which is exactly the size of the reclaim being investigated. Every number taken while diagnosing described a page shorter than the one being looked at, and the page appeared to "start working when the console opens". **Undock before measuring, or measure through Playwright.**
- **⚠️ THE SETTLE'S COMPENSATION MUST BE PUBLISHED THROUGH A RENDER, NOT WRITTEN IN THE rAF THAT MEASURES IT — AND THIS IS THE OPPOSITE OF WHAT IT LOOKS LIKE.** *(24 Aug, and it cost a deployed regression.)* The pinned chrome shrinks when it settles and a spacer grows by the same amount so the column's total never changes. Moving that write out of React state and into the `requestAnimationFrame` callback that measures the slab looks strictly better — no render sits between the measurement and the write — and it **broke every small scroll on every scrolling page**. The browser's scroll-anchoring pass does not account for a style set that way, so it takes the uncompensated delta out of `scrollTop` on each frame of the settle, and those deltas sum to the whole settle.
  - **MEASURED on Contact list, same commit, same build, one line different:** `set 10 → held 0 · 20 → 0 · 40 → 0 · 80 → 34` written imperatively, against `10 → 9 · 20 → 19 · 40 → 39 · 80 → 79` through state. The reader loses ~46px of position on any scroll shorter than the settle.
  - **THE GENERAL FORM: "fewer frames between measurement and write" is not the property that matters. What matters is that the compensation lands somewhere the browser's anchoring pass can see it.** Do not "optimise" this back into the rAF callback; it reads as an improvement and costs the reader their place.
  - **AND IT IS INVISIBLE TO EVERY LOCK THAT SCROLLS BY A LOT.** The measurement harness drives 300–600px, where 46px of loss is noise; the fault only shows on a scroll of the same order as the settle. A small-scroll hold check is the one that catches it, and it is what proved the mechanism both ways round.
- **⚠️ A PAGE THAT OVERFLOWS BY LESS THAN ITS CHROME IS TALL CANNOT SETTLE STABLY.** *(Same pack, found while building the withdrawn retract; recorded because the hazard is real whether or not anything acts on it.)* Settling reclaims height, and on a page whose scroller barely overflows that reclaim destroys the scroll the settled state is derived from. Measured: Noteboard's zone overflows by **47px** at 1440 against a 166px chrome — max scroll went 47 → 0, `scrollTop` clamped, the page un-settled, and the chrome grew back, **37 times on one downward pass**. Anything that increases what the chrome sheds must ask first whether the page can afford it, using the RESTING overflow — gating on the current figure re-creates the oscillation one level up, because settling is what makes the figure fall.
- **⚠️ THE `background` SHORTHAND RESETS `background-color` TO TRANSPARENT — so a gradient that fails to paint leaves NOTHING.** *(24 Aug, the masthead's parchment wash, and it is the fifth entry in a sequence about a see-through header.)* `background: linear-gradient(…)` is not "add an image"; it is the shorthand, and it sets every background longhand including the colour. The gradient itself then becomes the *only* fill: drop it — an unparsed stop, a token that resolves to nothing, a `color-mix()` an engine declines, a future edit that mistypes one hex — and the element is see-through, silently, with the rule still in the sheet looking correct.
  - **THE SHAPE: declare the colour and the image SEPARATELY**, so the worst case is a flat fill rather than a transparent one. `background-color: var(--mast-wash-bottom); background-image: linear-gradient(180deg, var(--mast-wash-top), var(--mast-wash-bottom));` — and make the colour the stop that meets the element's closing edge, so the fallback matches the wash where the hairline lands.
  - **⚠️ IT IS INVISIBLE TO EVERY CHECK THAT READS `backgroundColor`.** A lock asserting the fill is opaque by reading `getComputedStyle(el).backgroundColor` reports `rgba(0, 0, 0, 0)` for a *correctly* painted gradient — so the honest assertion covers the colour **and** every `rgb()` stop inside `background-image`. That distinction had to be added the day the flat fill became a wash, and asserting only the first would have been a lock that failed on a correct page while missing the real fault.
- **⚠️ A LOCK THAT COMPARES A THING WITH ITSELF SURVIVES CHANGES TO THE THING; ONE THAT COMPARES IT TO AN EXPECTED VALUE DOES NOT.** *(24 Aug — noticed because the wash needed exactly one lock amended and the harder one needed none.)* The pixel sweep proving nothing reads through the pinned chrome photographs the slab over two different backdrops **in the same posture** and requires the two images identical. When the flat fill became a gradient it needed **no change at all** — what the chrome is filled with never enters the claim. The sibling lock, which compared the computed fill against one expected colour, broke immediately and correctly.
  - **THE GENERAL FORM:** where a property must be *invariant*, assert the invariance directly rather than pinning the value the invariance currently produces. Pinning the value is a lock that goes red on every legitimate redesign — which trains the next person to rebaseline it without reading it — and, worse, the obvious loosening ("assert it is *not* the content's colour") passes vacuously.
- **⚠️ WHEN A SUITE REPORTS A FAILURE, GREP FOR THE ASSERTION'S TEXT TO FIND WHICH FILE OWNS IT — DO NOT ASSUME FROM THE NAME.** *(24 Aug, and it produced a confident wrong conclusion in two runs.)* A ten-file run went red on *"something between the scroll row and the content declares its own width"*. That sentence sounds like the content-geometry lock and lives in `matrix.measure.ts`. Re-running `contentGeometry.measure.ts` twice — once with the change, once without — produced **two clean passes and a conclusion that the failure was order-dependent state leakage**, which was about to be written up as a finding. The file simply does not contain the case.
  - **THE COST IS THE SHAPE, NOT THE MINUTES:** both runs were real, both readings were true, and both described a subject that was never in question — the same fault as measuring a harness instead of the app, or the deployed site instead of your bundle. **A green from the wrong file is indistinguishable from a green from the right one.**
  - **THE MECHANICAL STEP IS ONE COMMAND:** `grep -rln "<a distinctive phrase from the failure>" tests/e2e/`. Do it before re-running anything, and quote the file it names in the report.
  - **AND THE SECOND EXPERIMENT IS THE ONE THAT SETTLES AUTHORSHIP:** run the owning file against the baseline WITHOUT your change. Only that separates "my change did this" from "this was already red on main" — and here it proved the reds belonged to another stream's commit, which is a thing to report rather than to fix or to rebaseline.
- **⚠️ UNDER A DISPLAY-TOGGLING SHELL, A LOCATOR'S `.first()` ROUTINELY MATCHES A PAGE THAT IS NOT ON SCREEN.** *(24 Aug; the sibling of the portal-outliving-its-page note above, and it costs a timeout rather than a wrong reading.)* The workspace keeps every page MOUNTED and toggles `display`, and **three pages share `tpl-wpg`** — so `page.locator(".wpg.tpl-wpg .wpg-chrome").first()` resolves to a hidden grid and Playwright waits the full test timeout for it to become "stable", reporting *"element is not visible"* about a page that is perfectly visible. **Select the visible grid by measuring it** — `[...document.querySelectorAll(sel)].find(e => e.getBoundingClientRect().height > 0)` — then tag it and target the tag. Every lock in `tests/e2e/` that reads a `.wpg` already does this; a new probe is where the fault reappears.
  - **AND THE CENSUS IS SPLICED, NEVER RETYPED.** Writing the ten pages' route/class list by hand for a new probe produced **two wrong classes out of three** in one sitting (`aglist` for `agl-wpg`, `anl-wpg` for `qa-wpg`) — the same family as a test handing a function an input its callers cannot produce. Take the list from the lock that already has it.
- **⚠️ A PAGE'S RULE AND A COMPONENT'S RULE AT EQUAL SPECIFICITY: THE PAGE WINS, BECAUSE ITS SHEET IS LATER IN THE BUNDLE.** `.wpg--working > .wpg-scroll { padding-bottom: … }` is 0-2-0 and so is `.aglist .wpg-scroll { padding-bottom: 48px }` — so three pages silently discarded the grid's scroll-invariance padding, and *only* those three measured max scroll falling by 62 while the other six held. Nothing errors; the cascade is working as specified. **When a component and a page both need to contribute to one property, each contributes a TOKEN and the property is a `calc()` sum** (`padding-bottom: calc(var(--wpg-foot, 0px) + var(--wpg-reclaim-pad, 0px))`). Raising specificity is the wrong fix — it makes one contribution *replace* the other, which is the same bug pointing the other way.
- **⚠️ A GROUPED CSS RULE MAKES FIRST-MATCH SLICING AMBIGUOUS — declare per selector wherever a lock reads the file.** A stylesheet lock that finds its rule with `indexOf(".x {")` reads whichever block comes FIRST, so adding `.x, .y, .z { box-sizing: border-box }` above `.x`'s real rule silently repoints every assertion at a one-property stub. This has now caught `workspacePageGrid.css` **twice**: once as a genuine duplicate (`.wpg-scroll` declared twice, the lock reading the wrong half) and once inside the very commit that was fixing it — a grouped `box-sizing` rule added for three rows made `.wpg-scroll` ambiguous and the viewport lock reported *"row 3 stopped scrolling"* about a row that scrolls fine. **Two fixes, and prefer the first:** fold the shared property into each selector's own existing rule, so the file keeps one rule per selector (which `workspacePageGrid.css` states as its own invariant); or, where a group is genuinely right, make the helper join EVERY block for the selector, as `oneScreenTasks.test.tsx`'s `rule()` does. The failure is silent in one direction and a false alarm in the other, which is what makes it expensive both times.
- **⚠️ A BOUNDED-SLICE LOCK ASSERTS THAT BOTH ANCHORS EXIST BEFORE SLICING.** *(16 Aug — the same family as the source-string, prefix-match and off-screen-probe cases, and the one that hides longest.)* `indexOf` returns **`-1`** for a marker that is not there, and `slice(-1)` is read as *"one character from the end"* — so `src.slice(src.indexOf("function a"), src.indexOf("function b"))` **silently widens to the whole rest of the file** the day `function b` is renamed. Every assertion over it then covers code it was never meant to see, and it keeps passing until something downstream happens to contain the forbidden string. **The lock does not go red, it goes vague.** The worked example: the board's completion lock sliced `performBoardPlan` → `renderBoard`, `renderBoard` had been deleted, and *every function below `performBoardPlan`* was inside `not.toContain("done: true")` — which then fired on a correct new function and, worse, had been passing for the wrong reason for however long. **Use `src/test/sliceBetween.ts`** (`sliceBetween(src, from, to)` / `sliceFrom(src, from, len)`), which fails loudly naming the missing anchor. ⚠️ **THE SWEEP THAT INTRODUCED IT FOUND NINE MORE, ALL SILENT** — slices anchored on `renderFilterSection`, `renderFilterChips`, `renderTools`, `renderUserCard`, `ShellRail`/`ShellSide` and a `<header>` that `TasksPageLayout` does not have, every one of them reading an entire file. **Two were assigned and never read at all**, so they had asserted nothing since the day they were written. ⚠️ **AND THE FIX IS USUALLY NOT A NEW ANCHOR** — when the anchor is gone the SUBJECT is usually gone, so the honest replacement states the retirement (`expect(page).not.toContain("function renderFilterSection")`) and asserts the rule over the whole file, which is stronger than the bounded version ever was.
- **String-rendering specs — ANCHOR BEFORE YOU SLICE.** Component specs render through `renderToStaticMarkup` and assert against the HTML string (there is no jsdom in this repo — `vitest.config.ts` is `environment: 'node'`, and neither jsdom nor testing-library is installed). Whenever a spec **slices, splits or extracts** on a class or marker, assert that the marker exists FIRST — one `expect` per slice. A missing marker fails in one of two quiet ways: extracting yields `""` (`?? ""` / `?? []`) and every `.not.toContain` on an empty string passes; or `split(marker)[0]` yields the whole rest of the document, and whether the test notices depends on what happens to sit further down the page. Both go green while testing nothing. Prefer whole-string `toContain`/`toMatch` where it will do the job — `shellV2Smoke.test.tsx` never slices and is immune by construction. Where a slice is genuinely needed, restate its anchor inside each `it` that consumes it rather than relying on a `const` in the enclosing `describe`. (Audit + the failure it came from: `reports/string-spec-slice-audit.md`.)

## Multi-stream protocol (⚠️ SUPERSEDED 8 Jul by "Working discipline" above — kept for history; the shared-checkout model is retired in favour of one-session-per-worktree)
- **Identity gate:** any cross-session note (resume/sync/follow-up prompts) starts with self-identification from the session's OWN history; a note that reaches the wrong stream gets its facts verified, not obeyed — they may be stale (a "tsc is red" another session already fixed; a "pending deploy" that landed an hour ago).
- **Resume = re-read:** after any parking, in-context copies of shared files are stale by definition — re-read from disk before editing. Never edit another stream's uncommitted WIP (live lost-update risk); leave a handover note (BUILD-REPORT/CLAUDE.md/commit message) instead.
- **Commits:** explicit-path staging + `git commit --only -- <paths>` (race-proof against the shared index); `git diff --cached --name-only` must list only your stream's paths. No `git stash` / `checkout --` / `restore` / `clean` on anything, ever. Gates (tsc + production build + full Vitest) green before every commit — with `set -o pipefail` (piping to tail otherwise masks a red tsc, which also emits JS despite errors). If a gate is red from ANOTHER stream's untracked WIP, verify in an isolated HEAD worktree + only your files.
- **Reports:** per-stream report files (the `LOCATION_BUILD_REPORT.md` / `DISCOVER_PHASE1_REPORT.md` pattern). `BUILD-REPORT.md` is the legacy shared file — append-only, and a run note rides the SAME commit as its code (no floating hunks left in shared tracked files).
- **Test counts move several times a day across streams** (523 → 538 → 542 within 5 Jul alone) — record the suite figure fresh at commit time; never copy it from an earlier note or chat.

## Agent location / territory
- **Model:** the ONLY stored location data is `agent.country` (ISO 3166-1 alpha-2, e.g. `"GB"`) + optional `agent.city`, and `user.homeCountry` (ISO alpha-2). Everything else — the flag, the display name, the home-vs-foreign distinction, any market count — is **derived at read time** from those codes. Nothing territory-derived is stored on the agent, and **nothing is denormalised onto queries** (`recomputeQuery` is inert to location — recon-confirmed).
- **ISO alpha-2 is canonical.** Legacy full-name values (the name-based `COUNTRIES` in `agentOptions.ts` + the undeployed v12 Edit Agent drawer) are **tolerated at read time only** — `territory.ts` reverse-maps them to codes; consumers migrate to writing codes in Prompt 2.
- **Never `null`/`""`.** "Not set" always means the **key is omitted**. The `isValidAgent`/`isValidUser` rules reject a literal null (`data.x is string`). The signup seed (`homeCountrySeed()`) and quick-add both omit rather than write empty.
- **Single source of truth = `src/lib/territory.ts`** (Prompt 1): `COUNTRIES_ISO`, `QUICK_PICKS` (`GB US IE CA AU NZ`), `countryName`, `flagFor` (→ `flag-icons` class `"fi fi-gb"`), `isHomeMarket`, `detectHomeRegion` (browser locale region + tz fallback, **never IP**), `getHomeCountry` (stored ?? detected ?? `GB`), `homeCountrySeed`. Flags = the whole `flag-icons` SVG set, served as static assets (CSS-referenced, out of the main JS chunk), addressable by ISO code — **not** emoji (Windows renders flag emoji as letter-pairs).
- **`homeCountry`** seeded silently from the browser locale at signup, no onboarding step, no backfill (`getHomeCountry` covers absent users at read time), editable later in settings (Prompt 2/3).
- **Rules edited, NOT deployed.** The `homeCountry` clauses (`isValidUser` + the user-update allowlist) ride the **same `firestore:rules` deploy** as the already-in-file-but-undeployed `country`/`city` agent allowlist — **nothing location-related works in prod until that deploy lands.** Claude Code must not deploy.
